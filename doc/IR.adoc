= Ultraviolent IR

Status: design, reviewed with the user (2026-09-28, 2026-09-29). Stages A (this document
and the boundary tests), B (decode and shared semantics), C (the differential harness), and
D (block construction), E (the tier-0 executor, experimental), and F (the block cache and
its invalidation) are implemented; G and H are not. Review with the user before G.

This document designs the representation between the MIPS decoder and the fast execution
engines (ARCHITECTURE "The CPU is not the interpreter", "Future JIT architecture"): what a
unit of decoded code is, what executing it must preserve, how decoded code stays exactly
equivalent to the reference interpreter, and the order in which it is built.

== Performance objective

* **First target:** at least the configured guest clock in modeled guest cycles per host
  second on the representative workloads (`scripts/bench.py`: prom, boot, cpu, fs). For the
  180 MHz R10000 that is 180 M cycles/s; the reference interpreter runs 58-74 M (STATUS
  "Performance baseline").
* **Constraint:** every optimization preserves the benchmark digests and byte-identical
  snapshots taken at the same guest cycle.
* Tier 0 is not required to reach the target by itself. Its measured result decides whether
  the next work is further tier-0 overhead removal or tier 1 (the JIT).
* The reference interpreter is measured after stage B, and a material regression is
  investigated, but correctness and the oracle's simplicity come before keeping the
  reference engine the fastest interpreter.

== Why

Measured (STATUS "Performance baseline"): the reference interpreter spends most of each
guest instruction on work that does not depend on the instruction's operands. It fetches
through the host page cache, decodes the same word again, dispatches through two or three
switches, and returns a 32-byte `std::expected<Control, Exception>` through memory. An
engine that decodes each instruction once removes the repeated fetch and decode; a JIT
removes the dispatch as well. Both need the same decoded form.

== Execution rules every engine keeps

These are the reference interpreter's observable behavior. An engine that breaks one is
wrong, however fast. Stage A's tests pin the reference behavior they name.

. **Architectural state is `Cpu`'s.** Engines read and write `Cpu::state()` and
  `Cpu::fpu()`, and everything else through `Cpu` methods (MIPS.adoc "Structure"). No
  engine keeps a private copy of guest state.
. **Exact processor steps (ADR-018).** Every processor cycle is accounted for when it
  happens, by `Cpu::end_cycle(retired)` at the instruction boundary: cycles in which an
  interrupt, delayed watch, or instruction exception is taken retire nothing. Count is
  derived from cycles and Random from retirements, so an MFC0 of Count or Random, and every
  synchronized device access, sees the cycle position the reference interpreter would.
  Tier 0 does not batch cycle accounting. Any later batching needs block metadata that
  proves no instruction in the batch can observe or change the cycle position, and is its
  own reviewed change.
. **The run limit is mutable.** `Interpreter::run_until` takes its limit by reference: a
  device access during an instruction can lower it (an access schedules an event, and the
  machine moves its stop cycle). An engine rechecks the limit at every instruction
  boundary. Checks may later be removed only where block metadata proves that no
  instruction in the stretch can synchronously alter the scheduling boundary.
. **Pending exceptions at a boundary.** Before an instruction, if
  `Cpu::service_pending_exceptions()` takes an interrupt or delayed watch exception, the
  engine calls `end_cycle(false)` and leaves the block, exactly as `execute_cycle` does
  today. This is a different case from an exception raised by the instruction itself (next
  rule), although both end the block.
. **Instruction exceptions are precise.** A faulting instruction leaves the state of the
  instructions before it and none of its own; `Cpu::take_exception` then sets PC, EPC, BD,
  and the delay-slot state, the engine calls `end_cycle(false)`, and leaves the block.
. **Slow bus paths are barriers.** An instruction whose memory reference leaves the
  transparent host-memory path (any `Cpu::read` or `Cpu::write`: MMIO, uncached space, an
  unmapped or code-holding page) completes exactly; then the engine leaves the block and
  rechecks the run limit and pending exceptions before continuing. Such an access may have
  synchronized devices, run events, changed interrupt lines, changed bus mappings, or
  written code. Removing this barrier is a later optimization that needs its own proof.
. **Memory is the bus's.** Loads, stores, and fetches have the interpreter's translation,
  exceptions, byte order, uncached attribute, and device effects. Host-memory fast paths are
  allowed only where transparent, as the host page caches are today.

=== Scheduler invariant

No device, event, or DMA callback runs while an instruction is partly executed, except
inside a synchronized MMIO access made by that instruction, and none runs concurrently with
CPU execution. Events run where the machine synchronizes time: at the run limit, between
calls into the engine, and inside a `SynchronizedTarget` access. The IP27 machine enforces
this (`Ip27Machine::synchronize_time`) and `ip27.events_run_at_cycle_boundaries` tests it:
an event fires at the exact cycle its deadline converts to, and guest RAM it writes is seen
by the next instruction and not before.

Consequence: DMA into guest RAM happens either between engine runs or inside a barrier
access. A block never continues past a DMA write.

=== Mutable memory spans

`AddressSpace::writable_memory_bytes` returns host bytes that alias guest RAM. Contract: a
caller writes through the span synchronously, during the operation that obtained it, and
does not keep it across a return to the scheduler, to CPU execution, or to block
construction. Hub DMA (`Hub::Widget::xtalk_dma_write`) obeys this. The one retained
writable span is the CPU's own data page cache, which is `Cpu`'s and is invalidated by
`Cpu` (stage F). Code invalidation through `writable_memory_bytes` (below) covers exactly
the writers that obey this contract. A future DMA engine that kept a span would need its own
invalidation event.

== DecodedInstruction

`decode(std::uint32_t word)` is a pure function of the instruction word; `execute(Cpu&,
const DecodedInstruction&, std::uint64_t pc)` holds the semantics (`semantics.cpp`). The
reference interpreter is fetch, `decode`, and `complete_cycle` (execute, `apply_flow`, and
the cycle accounting). There is one copy of the MIPS semantics: every engine calls the same
`execute` and `complete_cycle`.

----
enum class DecodedOpcode : std::uint8_t {
    sll, srl, sra, ...        // one value per operation
    cop0_reserved,            // reserved CP0 encodings (CP0 usability is checked first)
    cop1, cop1x,              // the FPU, opaque in tier 0: execute_fpu(cpu, word)
    cop2,                     // COP2, LWC2, SWC2, LDC2, SDC2
    reserved,                 // every other reserved encoding
};

struct DecodedInstruction {   // 8 bytes
    DecodedOpcode opcode;
    Instruction instruction;  // the word; fields are extracted as the semantics use them
};
----

* `decode` classifies with one lookup in a 240-entry table, the index selected without
  branches.
* Checks that depend on Status (64-bit operations, MIPS IV, coprocessor usability) run at
  execution time, in the reference order, inside each operation's semantics, so a decoded
  instruction stays correct when Status changes after decoding. The order differs by
  operation (CP0 operations check usability before reserved encodings; COP1X checks MIPS IV
  before CU1), so it is code, not a flag set. The MIPS III gate, which the reference checks
  before anything else, is a table by opcode.
* Properties that blocks need (branch, ends a block, unsupported) will be a table by opcode
  in stage D, not per-instruction data.
* The FPU stays one opaque operation in tier 0.
* Tracing (`--trace cpu`) and PC probes keep using the reference interpreter.

Measured in stage B (2026-09-29): the first shape (24 bytes, fields pre-extracted into the
structure, decode out of line) made the reference interpreter 26-44% slower than the
nested-switch interpreter it replaced; the fields read back through memory and a second
jump table for the MIPS III gate were most of it. The 8-byte shape, an inline table-driven
`decode`, and a table gate recovered part of it. What remains (release build, `fs`: 16%
more host instructions and 23% more branch misses than before; about 25% slower on `fs`,
8% on `cpu`) is the cost of classifying separately from executing: one more
data-dependent step per instruction in the reference interpreter. Tier 0 decodes once per
block, so it pays this only when it builds a block.

== Blocks

A block is a run of decoded instructions that the fast engine executes without returning to
its dispatcher.

* **Source:** only host-backed instruction bytes (the CPU's code page cache) within one
  4 KiB virtual page. Page containment is a correctness rule, not an allocation size.
* **Length:** at most a conservative tier-0 maximum (initially 64 instructions; a tuning
  parameter measured in stage H).
* **Storage:** variable-sized. A block holds its instruction count and its operations in
  separately sized storage; no block reserves a page's worth of operations.
* **Ends:**
** after a branch or jump and its delay slot;
** before a branch or jump whose delay slot would fall on the next page (the reference
   step runs it);
** before the page boundary, or at the maximum length;
** after MTC0, DMTC0, ERET, TLBR, TLBWI, TLBWR, TLBP, CACHE, and SYNC (SYNC stays a
   terminator in tier 0, as a conservative choice);
** before any instruction tier 0 does not cover (`reserved`, COP2, and anything else
   listed as unsupported), which runs as a reference step.
* SYSCALL, BREAK, traps, and faults end execution when they are taken, not by rule.
* A block is entered only at its first instruction; other entry points have their own,
  possibly overlapping, blocks.

=== Construction (stage D)

`build_block(Cpu&, pc, Block&)` (`block.hpp`) builds one block into reusable storage:

* `Cpu::code_page(pc)` gives the host bytes of the code page where a fetch would take the
  host fast path. It translates and consults the memory map only (the code page cache fill
  of `remember_page`), never the bus: building a block cannot read a device.
* `operation_class(DecodedOpcode)`, a table by opcode, says whether an operation is plain,
  control (branch or jump), a state change, or unsupported.
* The result is a `Block` (start pc, page bytes, byte order, `BlockEnd`, and a vector of
  decoded operations sized by what was decoded), or a `NoBlock` reason: not host-backed, an
  unsupported first operation, or a first operation that is a branch whose delay slot cannot
  join it.
* Beyond the ends listed above: a branch whose delay slot holds another branch or an
  unsupported operation ends the block before the branch (`BlockEnd::delay_slot`); a state
  change in a delay slot stays with its branch; a branch and its slot are never split by the
  length limit.

=== Executor (tier 0)

At every instruction boundary, conservatively:

. stop if `cycles() >= limit` (the limit read through its reference each time);
. if `service_pending_exceptions()` took one: `end_cycle(false)`, leave the block;
. execute the operation; on an exception: `take_exception`, `end_cycle(false)`, leave;
. `apply_flow`, `end_cycle(true)`;
. leave if the instruction left the host fast path (a flag the CPU's slow paths set);
. leave if the next PC is not the next operation's (a taken branch out of the block, a
  nullified branch-likely slot);
. before each operation after the first, leave if its word in memory changed (a store
  through the host fast path into the block's page). Until stage F's frame generations, this
  per-operation load and compare is what keeps stores into code exact; it also covers the
  executing block, which is never freed.

Implemented as `BlockInterpreter` (`block_interpreter.hpp`, stage E). It builds the block at
pc on every entry (no cache until stage F), and records why it left each block
(`BlockExit`): completed, run limit, pending exception, exception, host path, left block
(pc is not the next operation's), code changed. A barrier includes the first access to a page
the host page cache has not seen, which goes through the bus. The machine runs it only when
selected (`Ip27Machine::set_execution_engine`, `--engine tier0`); tracing and PC probes
always use the reference interpreter.

Statistics (`BlockStatistics`, printed by `--engine-statistics`, collected per workload by
`scripts/bench.py --engine tier0 --statistics DIR`) are counted per block entry, not per
instruction: entries and operations executed; reference steps by `NoBlock` reason; built
blocks by length and by `BlockEnd`; executed operations per entry and exits by `BlockExit`.

A block starting in a delay slot (after a reference step ran the branch) needs no special
case: its first operation runs, `apply_flow` sends pc to the branch target, and the pc
check leaves the block.

== Keeping blocks valid

A block depends on the translation that found its bytes and on the bytes.

* **Selective translation tracking,** the host page model extended to blocks: a block
  records the TLB entry that mapped its page (none for unmapped segments) and its
  translation context (mode bits and ASID). A TLB write stales exactly the blocks derived
  from the entry written and from entries the write invalidated (`Cpu::forget_tlb_pages`'s
  mask). ASID and mode changes are part of the lookup key and stale nothing.
* **Global translation epoch** only for what selective tracking cannot represent: Config
  writes, reset, snapshot loads, and bus mapping changes (the existing
  `translation_generation_` and bus generation).
* **Code bytes:** each 4 KiB frame of a `MemoryBlock` that holds decoded code has a mark and a
  generation. Writers that can change it bump the generation: `AddressSpace::write` into
  memory, `writable_memory_bytes` (under the span contract above), and the CPU's slow store
  path. When a frame is first marked, the CPU drops its writable data-page entries for it,
  and afterward never caches a writable page into a marked frame, so every CPU store to
  code takes the slow path and is a barrier.
* **Lifetime:** invalidation never frees or overwrites a block; it makes blocks stale, and a
  stale block no longer matches a lookup. Blocks are replaced only on a lookup miss, and
  lookups happen only between blocks, so the block being executed stays intact even when
  its own code is written. The store completes, the barrier leaves the block, and the next
  lookup rebuilds.

=== The block cache (stage F)

* `BlockInterpreter` keeps a direct-mapped table of blocks, a power of two in size (default
  4096 entries, `--tier0-cache-entries`), indexed by `(pc >> 2) & (entries - 1)` and tagged by
  pc and translation context. An entry owns its block's operations; replacing it reuses
  their storage.
* An entry records its dependencies when built: the code epoch (`Cpu::code_epoch`, advanced
  whenever the host page caches are flushed: Config, reset, snapshot loads, bus remapping),
  a pointer to its frame's generation and the value, and the TLB entry that translated the
  page with that entry's generation (`Cpu::tlb_generation`, advanced for the entries a TLB
  write writes or invalidates). A lookup compares pc, context, epoch, frame generation, and
  TLB generation, and on a hit runs the cached operations: no fetch, decode, translation, or
  per-operation word check.
* Frames: `MemoryBlock` holds a mark and a generation per 4 KiB frame.
  `AddressSpace::write` and `writable_memory_bytes` report writes; a write to a marked
  frame advances its generation and clears the mark (`AddressSpace::code_writes` counts
  them). Building a block claims its frame (`Cpu::claim_code_frame`): the frame is marked and
  the CPU drops any writable data page it cached for it, and it never caches a writable
  page for a marked frame. So a CPU store into code always reaches the bus: it is a
  barrier, classified `code_store`, and the frame's blocks go stale. A write that clears the
  mark lets later stores to the frame take the fast path again until a block claims it again.
* Barriers are classified by the access that reached the bus (`Cpu::BusAccess`): a memory
  fill (a cached load or store that missed the host page cache), a device (MMIO or
  unmapped), uncached memory, a code store, or other (partial-word and conditional stores,
  watchpoints).
* Aliases: kseg0 and kseg1 views of the same code differ only above the index bits and share
  an entry, replacing each other; aliases through other virtual pages coexist and go stale
  together.

== Correctness method

* **Complete CPU state:** `Cpu::capture()` returns the architectural state in a comparable
  form: integer and FPU state, CP0 (Random computed), all TLB entries, the cache arrays,
  cycles, retirements, interrupt inputs, timer and watch state, compared field by field.
  Raw `StateImage` bytes are not used for comparison because structure padding is
  unspecified; snapshots keep using `StateImage`.
* **Differential tests** (`tests/arch/mips/differential.hpp`) run two identical CPU + RAM
  systems (no MMIO), one on the reference interpreter and one on the engine under test,
  from the same deterministic state, and compare `capture()`, the cache arrays, and RAM
  after every cycle, reporting the first difference. MMIO is never executed twice. Directed
  programs cover arithmetic, 64-bit gating in User mode, branches, branch-likely, delay
  slots, exceptions, coprocessor unusable, the FPU, Count/Compare boundaries, Random and TLB
  writes, interrupt lines raised between cycles, loads and stores, and fetch faults; 60
  seeded random programs add breadth. At stage C the engine under test is
  `PredecodedEngine`: instructions decoded ahead of execution and run through
  `complete_cycle`, falling back to a reference step wherever a fetch would not give the
  decoded word. The tests also check that the decoded path ran (no unexpected fallbacks).
* **Whole machine:** benchmark digests, and byte-identical snapshots at the same guest cycle.
  A full-machine lockstep mode with MMIO would need duplicated or restored machine state
  and is not planned.

== Stages

Each is one mechanism and one commit.

A. This document; tests of the execution-boundary assumptions; the scheduler invariant.
B. `DecodedInstruction`, `decode`, `execute`, `apply_flow`; the reference interpreter uses
   them. Digests and snapshots unchanged; the reference interpreter's speed measured.
C. `Cpu::capture()`, the differential harness, and single decoded instructions executed
   through the shared semantics against the reference interpreter.
D. Block construction without caching (formation rules above).
E. The tier-0 block executor with per-instruction boundary accounting.
F. The block cache and invalidation (TLB remaps, ASID and mode, virtual aliases of one
   physical frame, CPU stores and DMA into code, reset, snapshot load, bus mapping
   changes), memory-safe for the executing block.
G. Engine selection with the reference interpreter as the permanent oracle; all presets and
   all four workloads with identical digests and same-cycle snapshots.
H. Measure and optimize tier 0: boundary checks, dispatch representation, `ExecutionResult`
   traffic, block table size and block length, FPU handling. No tier-1 work.

A review follows stage C, before block construction.

If a stage would require duplicating instruction semantics, special-casing a guest PC,
weakening exact-cycle behavior, or making MMIO behavior hard to compare with the reference
interpreter, it stops and the conflict is documented here instead.

== Open questions

* Whether decoded blocks are worth keeping across snapshots (probably not: rebuild on load).
* Block table size and maximum block length for IRIX's working set (stage H).
* Whether the FPU leaves the opaque operation (stage H; the `cpu` workload spends about 4%
  in `execute_fpu`).
