= Ultraviolent 0.1.4 Release Notes

Ultraviolent 0.1.4 runs many machines on one host, and larger ones. Several machines can
share one installed disk through copy-on-write overlays, talk to each other through a
virtual Ethernet switch that needs no root, and run in the background, where `uvctl`
starts, stops, suspends, resumes, snapshots, clones, and attaches to them. A machine takes
more disks, on both SCSI buses. Rack systems grow from two modules to eight: up to 32 node
boards and 64 CPUs, with routers in a cube or hypercube. `USING.adoc` is the guide.

Ultraviolent ships no SGI firmware, media, or disk images. You supply your own PROM images
and IRIX discs (`assets/README.adoc`).

== What changed

* **Disks** (`USING.adoc` "Disks"; `doc/ORCHESTRATION.adoc` "O1"). `--disk` may be given
  more than once: the first is the system disk as before, the next ones take the next free
  units of the first SCSI controller, and `--disk 1:ID=FILE` puts one on the second.
  `ultraviolent disk create OVERLAY BASE` makes a copy-on-write overlay that holds only what
  the guest writes and reads the rest from BASE, which it never changes; `disk info` and
  `disk flatten` describe and copy them. `scripts/boot.sh` boots `disk.cow` when there is no
  `disk.img`.
* **Many machines** (`USING.adoc` "Many machines"; ORCHESTRATION.adoc "O2"-"O4").
  `ultraviolent switch SOCKET [--tap IFNAME]` is a virtual Ethernet switch; `--ethernet
  switch:SOCKET` plugs a machine into it, and `--ethernet-address` gives each its own MAC
  address. `--console-socket PATH` serves the console to whoever attaches. `--suspend FILE`
  writes the running machine to FILE when a signal stops it and resumes from FILE on the
  next run. `scripts/uvctl.py` puts these together from a fleet file.
* **Eight rack modules** (`doc/MULTINODE.adoc` "N4"). `--nodes` takes up to 32: four node
  boards per rack module, up to eight modules, whose routers form a cube (four modules) or a
  hypercube of sixteen routers (eight); `--express-links` also works with four modules.
  `--memory` is each node's memory; give large systems less (64 or 128 MB per node). IRIX
  boots on four modules (32 CPUs) in about three minutes; eight modules (64 CPUs) pass the
  PROM's discovery and diagnostics, but IRIX has not booted on them (Known limits).
* **Large machines on a small host** (`doc/SMP.adoc` "S4.5"; MULTINODE.adoc "N4"). Past 32
  CPUs, `--parallel` runs several CPUs on each host thread, one thread per host core
  (`--parallel-threads N` chooses): the PROM on 64 CPUs takes 368 s on the six-core
  reference host instead of 866 s with a thread each. A 32-node machine needs about 6 GB of
  host memory instead of more than 13: host-parallel CPUs no longer keep every old version
  of each node's address map, and the directory's back door no longer copies each entry to
  its aliases. Systems of more than sixteen nodes get premium directory DIMMs, which the
  PROM requires of them.
* **Benchmarks**: `prom32`, `boot32`, `cpu32`, `prom64`, `boot64`.

Systems installed with 0.1 to 0.1.3 keep working unchanged, and their snapshots load.

== Build

As 0.1 (`RELEASE-NOTES-0.1.adoc` "Build"): tag `v0.1.4`, Debian 13 on the reference host,
Clang 19.1.7 (`scripts/build-pgo.sh`) and GCC 14.2, CMake 3.31, no third-party dependencies.

== How it was checked

* `ctest` on the `dev`, `gcc`, `asan`, and `tsan` presets: all suites pass, with new tests
  for overlays, the switch, the console socket, disks on both SCSI buses, the hypercube's
  routes and configurations, freeing an address map's old versions, and the directory's
  regions.
* Benchmark workloads: the eleven one-, two-, and four-CPU digests and cycle counts are
  0.1.3's (`prom` through `reboot4`). `prom32` and `prom64` find every Hub and router and
  pass the PROM's diagnostics; `boot32` reaches `login:` (168 s) and `cpu32` runs.
* Installation from blank with the release's code (`scripts/rc-ip27-demo.py --tap uv0`): PROM
  log set up, five discs installed with the ssh server, cold boot, console and telnet
  logins, the keyswitch shutdown and power-off, a file kept across it, `sshd` running after
  the next cold boot, and `shutdown -i0`, in 0.28 hours of host time; no core dumps.
* Many machines (`scripts/fleet-demo.py` from that installation): two machines cloned from
  it on a virtual switch ping and telnet to each other; one is suspended, snapshotted,
  resumed, turned off with its peer, restored from the snapshot, and resumed into the
  snapshot's shell: 9 of 9 checks in 6.2 minutes.

== Known limits

As 0.1.3 (`USING.adoc` "Known limits"), and:

* Machines on a switch or TAP, and machines driven through their console socket, are not
  reproducible run to run, as with any outside input.
* IRIX does not yet boot on eight rack modules (64 CPUs): after "Starting up the
  system..." nothing more appears (STATUS "Current blocker"). Four modules (32 CPUs) boot.
  The `boot64` benchmark is there for that work and does not finish.
* A base image must not change while overlays use it; uvctl never changes one, but nothing
  stops another program from doing so (a changed size is refused, changed contents are not
  detected).
