= Many machines on one host: storage, networks, orchestration

Status: plan and progress, started 2026-11-23 (the user, after tier 2 and a review of the gap
between where the project is and VISION.adoc's end state: "lets plow the rest of 'can start
now' without stopping"). This document covers ROADMAP "Multi-machine orchestration" and the
host storage it needs. The other two parts of that push, large-machine speed and N4, are in
`SMP.adoc` "S4" and `MULTINODE.adoc`. arm64 hosts were dropped from the list by the user the
same day (ROADMAP "JIT").

== Why

VISION.adoc's success case is several virtual SGI systems on one Linux host, talking to each
other and to real machines. Each piece of that already runs once: one machine, one TAP, one
disk image of 9 GB, a console on standard input. What is missing is the host side:

* a second disk, and disks that share a base image, so that ten machines need not be ten
  copies of an installed IRIX;
* a network between machines that needs neither root nor a Linux bridge per machine, and
  can be joined to the host's own network;
* a console that can be reached after the machine was started in the background;
* a tool that starts, stops, suspends, resumes, snapshots, and clones machines described in
  one file.

None of it is guest-visible beyond what real hardware already offers (more disks on the
BaseIO's SCSI buses, an Ethernet cable to a switch, a serial console), so it needs no new SGI
evidence. All of it is backend work: "Backends own host integration" (ARCHITECTURE.adoc).

== Stages

Each stage ends with the dev suite passing, the benchmark digests unchanged, and STATUS
updated; the last stage also runs gcc, asan, and tsan.

* **O1, storage.**
** More disks: `--disk [BUS:ID=]FILE`, repeatable. Without a placement the first disk is the
   system disk (bus 0, ID 1, as now), the next ones IDs 2, 3, 4, 5, 8, ... of bus 0 (6 is
   the CD-ROM, 0 the controller). Bus 1 is the BaseIO's second SCSI channel, as on slate
   (OBS-SLATE-0001: two QLogic controllers). IRIX names them `dks0d2`, `dks1d1`, ...
** Copy-on-write disks: an overlay file that holds only the blocks written since it was made
   from a base image (`ultraviolent disk create OVERLAY BASE`); reads of unwritten blocks
   come from the base, which is opened read-only and may be shared by any number of
   machines. The format is Ultraviolent's own (below), and `ultraviolent disk commit`
   folds an overlay into a plain image.
** A store on `pread`/`pwrite` in place of a stream that seeks, and the host's share of a
   disk-heavy workload measured, to decide whether a faster backend (io_uring, direct I/O) is
   worth its code. Measured first; the vision's "NVMe" is a host-file question until a
   measurement says otherwise.
* **O2, a virtual Ethernet switch.** `ultraviolent switch SOCKET [--tap IFNAME]` runs a
  learning switch on a Unix socket; `--ethernet switch:SOCKET` plugs a machine into it. With
  `--tap` one port is a host TAP, so the switch's machines reach the host and, through a
  Linux bridge, the network. `--ethernet-address` gives each machine its own MAC address
  (and so its own Ethernet NIC serial number). Runs on a switch are not deterministic, as
  with a TAP.
* **O3, the console on a socket.** `--console-socket PATH` serves the console on a Unix
  socket: what the guest prints goes to standard output (a log) and to the attached client;
  what the client types goes to the guest. A machine started in the background can then be
  attached to and detached from.
* **O4, `uvctl`.** A fleet file (TOML) names machines (PROM, memory, CPUs, nodes, disks, the
  switch each Ethernet port joins, the console socket) and switches. `uvctl` starts and stops
  them (`up`, `down`: the keyswitch, so IRIX shuts down cleanly), `suspend` and `resume`
  (a snapshot of the running machine, and a run from it), `snapshot` and `restore` (state,
  overlays, flash, and NVRAM of a stopped machine under a name), `clone` (a new machine whose
  disks are overlays on another's), `console`, and `status`. Acceptance: two machines cloned
  from one installed disk, on one switch, each given its address on the console, ping each
  other and log in to each other with telnet; one is suspended and resumed and still answers.

== Copy-on-write overlay format

Little-endian. The header is one 4096-byte block:

----
0    8  magic "UVCOW\0\0\1"
8    8  virtual size in bytes (the base's size when created)
16   4  cluster size in bytes (65536)
20   4  length of the base path in bytes
24   8  offset of the bitmap (4096)
32   8  offset of the first cluster (the bitmap's end, rounded up to the cluster size)
40   *  the base path, UTF-8, relative to the overlay's directory unless absolute
----

The bitmap has one bit per cluster (bit `n % 8` of byte `n / 8`), set when the overlay holds
that cluster. Cluster `n` is at `first + n * cluster_size`; the file is sparse, so it takes
only the space of the clusters written. A write to a cluster the overlay does not hold reads
the whole cluster from the base, merges the written bytes, writes the cluster, and only then
sets and writes the bitmap byte: an interrupted write leaves the cluster unclaimed, and the
guest's view is that of a write that did not happen, as with a disk that lost power.

== Progress

* **O1, storage (2026-11-23).** `Ip27Machine::attach_disk(bus, id, store)` puts a disk at
  any free ID of either BaseIO SCSI bus; its state is saved under `scsiB.targetI`, so the
  system disk's key (and old snapshots) are unchanged. `--disk [BUS:ID=]FILE` is
  repeatable. `backends::CowBlockStore` is the overlay above; `open_disk_image` opens a
  plain image or an overlay, and `ultraviolent disk create|info|flatten` manage them
  (`src/disk_command.cpp`). `FileBlockStore` now uses `pread`/`pwrite`. Tests:
  `backends.cow.*` (reads through, writes stay in the overlay across a reopen and a
  partial last cluster, chains, the base's size checked), `ip27.disks_on_both_scsi_buses`.
  Observed with the installed IRIX of the 0.1.3 release check (`local/o1`): the system
  disk as an overlay on it, a 1 GB overlay as `dks0d2`, a plain 512 MB image as `dks1d1`;
  `hinv -c disk` lists "unit 1 on SCSI controller 0", "unit 2 on SCSI controller 0", "unit 1
  on SCSI controller 1"; a write to `/dev/rdsk/dks0d2vol` reads back in IRIX and on the host
  only through the overlay; a file written on the root file system survives a cold boot
  from the overlay; the base's modification time is unchanged; the system overlay holds 196
  clusters (12 MB) after two boots. Measured: on `fs`, the disk-heavy benchmark, the host
  kernel is 11.6% of host time and most of that is page clearing and the snapshot's load;
  the copies of disk reads are about 2%. A faster storage backend (io_uring, direct I/O)
  would save at most that, so it is not built (decided: positioned reads and writes are
  enough until a workload shows otherwise).
* **O2, the switch (2026-11-23).** `backends::SwitchTable` (learning, flooding, aging,
  forgetting a port that leaves), `SwitchServer` (a `SOCK_SEQPACKET` Unix socket, one
  message per frame, optionally a TAP port; a port whose queue is full loses the frame),
  `SwitchLink` (the guest's cable; if the switch goes, the cable is unplugged), `ultraviolent
  switch SOCKET [--tap IFNAME]` (`src/switch_command.cpp`), `--ethernet switch:SOCKET`, and
  `--ethernet-address` (the Ethernet NIC's record and serial number follow it). Tests:
  `backends.switch.learns_and_floods`, `backends.switch.carries_frames_between_links` (three
  links through a real socket: flood, learned reply, a port that disconnects).
* **O3, the console socket (2026-11-23).** `backends::ConsoleSocket`: one client at a time
  on a Unix stream socket, the last 4 KB replayed on attach, input read through
  `TerminalInput` (so Ctrl-] monitor commands work there too), output also to the scripted
  console, which writes the log and recognizes prompts. `--console-socket PATH` (not with
  `--interactive`). Test: `console_socket.attach_replay_type_detach`.
* **O4, `uvctl` (2026-11-23).** `scripts/uvctl.py` as planned, with one addition to the
  emulator: `--suspend FILE` resumes from FILE when it exists (and deletes it once loaded: the
  disks move on from there) and writes FILE only when a signal ends the run, so a machine
  that powered off is never resumed from a stale state. Snapshots and clones freeze the
  disk into `layers/` (read-only) and put the machine on a new overlay of the same name, so
  neither copies a disk and the fleet file stays right. Acceptance, `scripts/fleet-demo.py
  --from local/release-check-013` (the 0.1.3 release check's installed disk): 9 of 9 checks
  in 6.2 minutes (`local/fleet-demo/results.txt`): alpha created on an overlay and beta
  cloned from it; both up on switch `lan` with different Ethernet addresses; beta pings
  10.77.0.1 (3 of 3) and logs in to alpha with telnet, reading a file only alpha has; beta
  suspended, snapshotted, resumed, and its shell pings alpha again at once; both powered off
  by the keyswitch; beta restored to the snapshot and resumed: its file holds the
  snapshot's "before-suspend", not the later "after-resume", and alpha's address does not
  answer. The installed base disk was only read.
