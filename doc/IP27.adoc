= IP27 Machine Personality

This note records the IP27 (Origin 200/2000 node) facts the `machines/ip27` personality
relies on, and what it deliberately leaves unmodeled. It grows milestone by milestone.
`IP27-TARGET.adoc` defines the target configuration; this file is the hardware-facts record
for it.

== Node address space

* Software addresses on IP27 select an address class with their top byte (PRM §3.3.1.5,
  Table 3-4; §1.2.2): `documented`.
+
[cols="1,1,3"]
|===
|Top byte |Class |Meaning (PRM)

|`0x90` |HSPEC |PROMs, back-door directory memory
|`0x92` |IO |I/O windows, including Hub and Bridge registers
|`0x94` |MSPEC |(not described)
|`0x96` |UNCAC |bank 0 memory, uncached
|`0xa8` |CAC |bank 0 memory, cached
|===
+
These are R10000 xkphys addresses (UM 16.2). `0xa8` is cache algorithm 5, cached. `0x90` to
`0x96` are cache algorithm 2, uncached, with uncached attributes 0 to 3 in VA[58:57]. The
Hub therefore tells HSPEC, IO, MSPEC, and UNCAC apart by the uncached attribute, and memory
from HSPEC by the request kind. In system-address terms (ADR-019): CAC is a cached request;
HSPEC, IO, MSPEC, and UNCAC are uncached requests with attributes 0, 1, 2, and 3. `inferred`
from PRM Table 3-4 and UM 16.2, 6.23.
* The node ID (NASID) occupies physical address bits 39:32, and node IDs are 0 to 255 (PRM
  §1.2.1, §1.2.2, Table 3-4 `n:` examples): `documented`. Before node IDs are assigned they
  are all zero (PRM §1.2.3). With one node the NASID stays 0; with two, each node's view of
  addresses follows the node IDs (SMP.adoc "S5: the second node", "Progress" S5.1).
* Memory banks are 512 MB apart: `b:#` adds bank × 512 MB (PRM Table 3-4). `documented`.

=== HSPEC (uncached, attribute 0)

From LINUX `addrs.h` (`inferred`):

[cols="1,1,3"]
|===
|Offset |Name |Behavior

|`0x00000000`–`0x0fffffff` |UALIAS |uncached references to the node's own memory. The bottom
128 KB is flipped by address bit 16 for CPU B, so each CPU has private low memory.
|`0x10000000`–`0x1fffffff` |LBOOT |the local Hub's boot PROM and other directory-bus devices
(PRM names `h:256m` = `0x9000000010000000` LBOOT: `documented`)
|`0x30000000`–`0x3fffffff` |RBOOT |the boot PROM of the node whose HSPEC space this is
(`NODE_RBOOT_BASE`, "Hub's RBOOT space")
|`0x80000000`–`0xbfffffff` |back door ECC |memory ECC (PRM Table 3-4 `E:`)
|`0xc0000000`–`0xffffffff` |back door directory |protection and directory entries (PRM Table
3-4 `L:`, `H:`, `P:`); see "Memory and directory"
|===

The R10000 reset vector `0xffffffffbfc00000` is an uncached attribute-0 reference to physical
`0x1fc00000` (UM 17.2, 16.2). That lies in LBOOT.

=== IO (uncached, attribute 1)

* I/O space is divided into 16 MB "small windows", one per widget: offset = widget << 24
  (LINUX `SWIN_SIZE_BITS`; PRM Table 3-4 `w:` "sets bit 24, adds widget", example
  `i:(16m+32)` = `0x9200000001000020`). `inferred`, consistent with PRM.
* Widget 1's window starts with the local Hub's own registers: IALIAS, 8 MB at
  `0x92000000_01000000` (LINUX `HUB_REGISTER_WIDGET`, `IALIAS_BASE`). `inferred`.
* Hub register sections within IALIAS (LINUX; names `documented` in PRM §3.4): PI
  (processor interface) `0x000000`, MD (memory/directory) `0x200000`, MD junk bus
  `0x220000` (LEDs `MD_LED0` `0x220050` for CPU A and `MD_LED1` `0x220058` for CPU B), II/IIO
  (I/O interface) `0x400000`, NI (network interface) `0x600000`.
* Big windows (M mode, LINUX `sn0/addrs.h`): seven of 512 MB from I/O offset 512 MB, each
  translated to a widget and crosstalk offset by its IIO_ITTE register at every access
  (`Hub::BigWindow`). Fields (`hypothesis`: as the IRIX-derived Linux 2.4
  `asm-ia64/sn/sn1/hubio.h` gives them for the Bedrock): crosstalk offset bits 4:0 in 512 MB
  units, widget bits 11:8. `observed`: the PROM writes every ITTE 0 at 5.3 s; IRIX keeps
  ITTE 7 at 0 (widget 0: the top window "as a surrogate for the first small window",
  `sn0/hubio.h` SWIN0_BIGWIN) and parks ITTEs 1–6 at `0x300`. `hypothesis`: an ITTE resets
  to 0.

== Boot PROM

* The IP27 Flash PROM is an AMD 29F080: 1 MB in 16 pages of 64 KB. Pages 0–13 hold the
  IP27PROM code; pages 14–15 hold the PROM log (environment variables, lists, error log),
  which persists (PRM chapter 5): `documented`.
* IP27PROM images are distributed in `promgen` format with the extension `.img`
  (PRM §2.4): `documented`. The user's `ip27prom.bin` has this layout (IMAGE, `observed`):
+
[cols="1,3"]
|===
|Offset |Content

|`0x40` |ASCII `JFKSWCSM`
|`0x50` |u64 total file size (912,848)
|`0x80` |ASCII `ip27prom`
|`0x98` |u64 header size (4,096)
|`0xa0`, `0xa8` |u64 `0xc00000001fc00000`
|`0xb0`, `0xd0` |u64 payload size (908,752 = file size − header size)
|===
+
The payload begins with a table of jump/NOP pairs, consistent with the R10000 exception
vectors at `0xbfc00000` + 0x000/0x200/0x280/0x300/0x380 (UM Table 17-1). The prototype
executed the payload from `0x1fc00000` coherently. `observed`.
* The flash is visible at the base of LBOOT: the PROM reads its `ip27conf` block at HSPEC
  `0x10000060`–`0x1000008f` (`observed`). It is also visible at HSPEC `0x1fc00000`, where the
  reset vector points, and at the base of RBOOT (`observed`: the PROM reads the processor
  clock at RBOOT + `0x70` and divides it by 10^6). `hypothesis`: those are the only 1 MB
  windows. Where the rest of LBOOT and RBOOT decodes is unknown.
* `hypothesis`: flash bytes the image does not provide read as `0xff` (erased NOR flash).
  The PROM log pages start erased until a persistent flash backing exists (M3).
* The flash is `devices::Am29f080` (AMD Am29F080 datasheet): read array; reset (`F0`);
  autoselect (manufacturer `0x01`, device `0xd5`, sectors unprotected); byte program
  (clears bits only); sector and chip erase; while a program (7 µs) or erase (1 s per sector)
  runs, reads return status: DQ7 data polling, DQ6 toggle, DQ5 for a program that tries to
  set bits, DQ3 during an erase. Command cycles decode A10–A0. Erase suspend is not modeled.
* Wiring, `observed` in the PROM's flash driver: command and program writes put flash address
  A at LBOOT + (A << 3) with the data in bits 7:0, so they span 8 MB of LBOOT (sector 14's
  erase goes to LBOOT + `0x700000`); reads are byte-addressed (manufacturer ID at +0, device
  ID at +1). The machine maps the first megabyte of LBOOT, the reset-vector window, and RBOOT
  onto the flash array for reads while the flash is in read-array mode and remaps them to
  the flash in command modes; writes always reach the flash, and LBOOT/RBOOT + 1 MB to 8 MB
  take writes only (`hypothesis`).
* Persistence: `ultraviolent --flash FILE` loads the flash from FILE when it exists and writes
  it back when a run changed it; the PROM image file is never written. Snapshots carry the
  flash contents.
* `observed`: with the flash modeled, POD's `initlog` (after `go cac`; "Can't initialize PROM
  log while running out of PROM" in Dex mode) erases the PROM log sectors and writes its
  header; the next boot's BASEIO PROM gets past "Cannot assign moduleid".

== Memory and directory

* `Ip27Config::memory_bytes` fills 512 MB banks from bank 0; a final partial bank must be a
  power of two of at least 8 MB (MD_SIZE_8MB, IRIX-derived `hubmd.h`). The default is one
  512 MB bank. Each bank has two memory DIMMs and one directory DIMM slot (PRM 1.4).
* `hypothesis`: installed memory is contiguous from physical 0 (bank 0 first, banks 512 MB
  apart per PRM). It is reached by cached references (CAC), uncached attribute-3 references
  (UNCAC), and uncached attribute-0 references within UALIAS (first 256 MB). The bank sizes
  programmed in MD_MEMORY_CONFIG do not change the decode yet, and memory addresses beyond
  a bank's installed size are unmapped rather than aliased.
* The CPU B UALIAS flip is not modeled, because the target has one CPU (slice A).

=== Directory memory

`DirectoryMemory` is the back-door view of the directory at HSPEC + 3 GB (IRIX-derived
`addrs.h` BDDIR_ENTRY_LO/HI and BDPRT_ENTRY; PRM Table 3-4, whose `L:0x2100560` =
`0x90000000c08402a0` is a unit test). Each 4 KB page of memory has 1 KB: 64 protection
doublewords (one per region), then (address bit 9) 32 directory entries of two doublewords,
one per 128-byte line. Bank b's entries start at b × 128 MB.

* Directory DIMMs are standard (`Ip27Config::directory`, default; `hypothesis`: the
  configuration that needs no directory DIMMs) or premium. An entry holds 16 bits
  (MD_SDIR_MASK) or, with premium DIMMs while MD_MEMORY_CONFIG DIR_PREMIUM is set, 48 bits
  (MD_PDIR_MASK). Bits beyond the entry, including MD_DIR_FORCE_ECC, are not stored.
* `hypothesis`: a bank's DIMMs ignore address bits above their size, so back-door addresses
  beyond the installed directory alias within it.
* `hypothesis`: an empty bank's directory reads zero and ignores writes.
* `hypothesis`: ECC fields hold what is written; hardware ECC generation and checking are
  not modeled. The ECC back door (HSPEC + 2 GB) is not modeled.
* Only doubleword accesses are modeled.

`observed` (flash `0x1fc28290`, `0x1fc28460`): MDIRCONFIG sizes each bank through the
directory. It writes a pattern to the bank's first protection entry and a different value to
the next, and reads the first back: 48 bits intact means premium, low 16 bits `0x5555`
standard, anything else an empty bank. It then writes the entry for base + size/2 for sizes
512 MB down to 32 MB and checks whether the base entry changed (aliasing). For a 512 MB bank
it also checks that data 64 MB apart does not alias. With the default configuration it
programs MD_MEMORY_CONFIG = `0x00101fa80f000007`: bank 0 is 512 MB (code 7), the other
banks empty, DIR_PREMIUM clear.

== Processor

* R10000 (IMAGE: build flags `-DR10000 -mips4`). The build flags also include
  `IP27_CONFIG_SN0_1MB_90MHZ`, `-DDISABLE_JUNKUART`, and `-DIOC3_UART` (IMAGE, `observed`).

=== Reset mode bits

The flash carries a configuration block (IMAGE, `observed`):

[cols="1,3"]
|===
|Flash offset |Content in the user's image

|`0x64` |R10000 mode word `0x1211a785`
|`0x68` |ASCII `ip27conf`
|`0x74` |180,000,000 (processor clock, Hz)
|`0x7c` |90,000,000 (Hub clock, Hz)
|`0x84` |1,250,000 (real-time counter clock, Hz; matches LINUX `NSEC_PER_CYCLE` 800)
|===

Early in reset the PROM loads the word at LBOOT + `0x64` into Config and compares Config's
bits 15:0 and 24:16 with it. On a mismatch it stores failure code `0xb4` and leaves the normal
path (`observed`). The CPU's Config at reset is therefore bits 24:0 of this word (UM 8.5), plus
the hardwired 32 KB primary cache fields: `0x6c11a785`. `inferred`: the node presents this
word as the R10000 mode bits. Decoded (UM Table 8-1): K0 = 5, PrcReqMax = 3, SysClkDiv code
3 (divide by 2), SCBlkSize = 32 words, big-endian, SCSize = 1 MB, SCClkDiv code 2.
`Ip27Config::cpu.config` applies only to images without this block.

The processor clock defaults to 180 MHz, consistent with the block.

`--cpu r12000` (`Ip27Config::processor`) fits R12000s instead: PRId and the FPU's
implementation word `0x0e35`, revision 3.5 as slate's (OBS-SLATE-0004), the R12000 processor
model, otherwise the R10000's behavior (SMP.adoc "S6: IP31 / R12000"). The clocks and the
reset mode word still come from the flash block, so with the user's image the guest reports
180 MHz. Snapshots record the PRId the guest booted with (`machine.processor_id`; absent, the
R10000 default) and refuse another.

== Machine loop and time

* Virtual time is `time_at_cycles(cycles, processor clock)` of the CPU's completed cycles.
  The machine brings the scheduler up to that time at the first cycle boundary at or after
  the next event deadline (events fire there), and immediately before any device access
  (devices see the time at the start of the accessing instruction). Deterministic by
  construction (ADR-005, ADR-018).
* Host pacing (`--realtime`, for interactive use; ARCHITECTURE.adoc "Wall clock may pace a
  guest"). `backends::RealTimePacer` compares virtual time since the start of the run with
  host time since then; main's host check event (every 10 ms of virtual time, the one that
  also reads the stop flag) asks it how long to wait and passes that to
  `Ip27Machine::hold_host_until`. The machine does not wait in the event: an event can run
  under the device lock (host-parallel CPUs), where the other threads would spin. Each run
  loop waits where it holds nothing: the one-CPU and turn-taking loops before their next
  engine run, each CPU thread at the top of its loop, parked (a thread at the window leaves
  its wait for this too). Only host time is spent: a paced run without input ends in the same
  state as an unpaced one (`ip27.host_hold`, and the idle measurement in STATUS.adoc). When
  the host falls behind, the run goes unpaced until it catches up, by at most a second; older
  lag is forgotten (a boot that runs slower than real time, a stopped process), so the guest's
  clock then trails the host's by that much.

one lists its evidence. Only doubleword accesses are modeled. Any other access is refused
(reads take a bus error; writes are lost) and traced under `hub`.

=== Vector PIO

Route-addressed access between NIs, used before node IDs exist (LINUX `hubni.h` field
masks; the PROM's protocol in SMP.adoc "What is known", `observed` by disassembly). A write
of NI_VECTOR_PARMS (PIO ID 49:40, write ID 39:32, address 19:3, type 1:0: read 0, write 1,
exchange 3) sends the request along NI_VECTOR with NI_VECTOR_DATA. The address is an offset
in the target's NI space (`observed`: discovery reads offset 0, NI_STATUS_REV_ID, and the
global master writes each node ID to `0x108`, NI_SCRATCH_REG1).

Model (`hypothesis` unless noted): with no router every route ends at the neighbor Hub, and
the response arrives before the requesting CPU's next access. The target serves the request
on its own NI registers (an exchange returns the old value and writes the new). The
response sets NI_VECTOR_STATUS: VALID 63; OVERRUN 62 when an earlier response was not
cleared; the request's PIO ID, write ID, and address; and its type, or 4 (address error)
when the target has no register there, 5 (command error) for type 2. TARGET (60:51) and
NI_RETURN_VECTOR are 0. A read or exchange puts the value in NI_VECTOR_READ_DATA, which
software can also write (`observed`: the PROM writes `0xdeadbeefdeadbeef` there before a
read). Reading NI_VECTOR_CLEAR returns the status and clears it; NI_VECTOR_STATUS and
NI_RETURN_VECTOR ignore writes. On one node a request goes nowhere and no response arrives.

=== The Hub over crosstalk

The Hub is a crosstalk widget on its Crossbow port. Its widget configuration space starts at
II offset 0 (IIO_WID at `0x400000` is WIDGET_ID, `inferred`). `inferred`: its whole local
register space (PI, MD, II, NI) also answers at crosstalk offset `0x1000000` + the local
offset, 64-bit. `observed`: with two nodes, the PROM's `xbow_update` (`0x1fc3a3a4`) aims big
window 1 at the peer Hub's Crossbow port (ITTE `0x1900`) and reads its node ID (bits 16:8)
at `0x1600000`, NI_STATUS_REV_ID; without the window it printed "xbow_update: Could not get
slave nasid".

=== MicroLAN

MD_MLAN_CTL (IRIX-derived `hubmd.h` MLAN_*): PHI1 33:27 and PHI0 26:20 (timing), PULSE 19:10
(low-pulse length), SAMPLE 9:2 (sample time), DONE 1, RD_DATA 0 (the sampled line). A write
starts a pulse and sample; it resets to PHI1 = PHI0 = `0x31`.

`observed`: the PROM's first operation is a 520-unit pulse sampled at 65, a 1-Wire reset
and presence detect; it tries three times and continues without a serial number.

Model: each node's bus (`Node::mlan`) carries its NICs ("NICs"); a write performs the
operation on it with the MCR encoding, and RD_DATA returns the sampled line, 1 with nothing
attached. `hypothesis`: an operation completes before the next access.

=== Block-transfer engines

Two engines, at `0x410000` and `0x420000` (IRIX-derived `hubio.h`): IBLS length/status
(length 15:0, ERROR 16, BUSY 20), IBSA source, IBDA destination, IBCT control (ZFIL_MODE 0,
NOTIFY 4, POISON 8), IBNA notification address, IBIA interrupt address (level 22:16, node
8:0).

`observed` (NMI_INIT, LED `0x5b`): the PROM writes IBLS = BUSY | `0x1000`, the source and
destination (cached xkphys addresses), IBIA = level 63 (BTE 0) or 62 (BTE 1), then IBCT =
0, and polls PI_INT_PEND0 for both levels. The public Linux SN1 BTE driver uses the same
sequence (IBCT starts the transfer).

Model:

* Writing IBCT while IBLS.BUSY is set runs the transfer: IBLS length × 128 bytes (`inferred`:
  the PROM splits a region between the engines at `0x1000` lines = 512 KB) from IBSA to IBDA,
  or zeros with ZFIL_MODE, through the node's address space using address bits 39:0
  (`hypothesis`).
* `hypothesis`: without BUSY, writing IBCT starts nothing (INITII zeroes every register).
* On completion IBLS reads 0 (ERROR if an access failed), the final IBLS is written to IBNA
  with NOTIFY, and IBIA's level is set in PI_INT_PEND when IBIA names node 0.
* `hypothesis`: a transfer completes before the next access; its duration is not modeled.
  POISON is not modeled.

==== Register survey

To list the Hub registers a stretch of PROM execution touches, build a temporary binary that
answers every unmodeled Hub read with 0 and logs the offset, run it from a snapshot, and
model each register from its evidence. The survey binary is never committed and its answers
are never evidence: a register enters `hub.cpp` only with a cited source.

=== Hub interrupts

From the IRIX-derived `asm/sn/intr.h` (`inferred`):

* Writing `0x100 | level` to PI_INT_PEND_MOD sets pending interrupt `level`; writing `level`
  clears it. Levels 0–63 are INT_PEND0 bits, 64–127 INT_PEND1 bits.
* Each CPU slice has INT_MASK0/1. CPU A's `INT_PEND0 & INT_MASK0_A` drives R10000 IP2, and
  `INT_PEND1 & INT_MASK1_A` drives IP3 ("L2 = INT_PEND0, L3 = INT_PEND1"). The machine
  connects them to CPU interrupt inputs 0 and 1.
* L4 (RTC): `PI_RT_PEND_x & PI_RT_EN_x` drives IP4 (HUB_IP_RT); L5 (profiling):
  `PI_PROF_PEND_x & PI_PROF_EN_x` drives IP5 (HUB_IP_PROF); machine inputs 2 and 3. The RT
  comparator for a CPU pends when PI_RT_COUNT reaches PI_RT_COMPARE_x; the profile comparator
  pends both CPUs. `inferred`: a pending bit stays set until software writes it, and a compare
  value already passed does not fire until the counter comes round (IRIX's clock tick).
* Crosstalk interrupt packets to PI_INT_PEND_MOD set their vector's level; clear packets (a
  Bridge's INT_MODE) clear it (`hypothesis`).
* L6 (Hub errors) is not modeled.

The PROM sets level 113 (`IP27_INTR_4`, "reserved for PROM use") during its first barrier
(LED `0x28`) and reads it back from INT_PEND1 (`observed`).

=== Two CPUs on a Hub

Stage S0 of `SMP.adoc`. Observed on the user's image (IMAGE) by disassembly and by logging
the Hub accesses of a run in which PI_CPU_PRESENT_B reads 1 but no second CPU executes:

* Both CPUs run the same reset code from the reset vector. The first Hub access after
  setting Status reads PI_CPU_NUM (`0x1fc0082c`) and indexes the LED registers by it; a
  second read (`0x1fc008a8`) spins 128 iterations when it is nonzero, so CPU B trails A.
  The PROM reads PI_CPU_NUM about a hundred more times in its LED macro. `observed`.
* The two CPUs meet in memory, not in the Hub (routine at `0x1fc58788`): each records
  progress code `0x24` in its own slot of a per-CPU table, reads PI_CPU_PRESENT_A and _B,
  and, when both are 1, polls the other CPU's slot for `0x24` up to 200,000 iterations.
  On a timeout it writes 0 to the other slice's PI_CPU_ENABLE (A writes ENABLE_B at
  `0x1fc58850`) and records the loss in a PROM variable; when either PRESENT bit is 0 it
  takes the same path at once. `observed`. No Hub register is read during the poll.
* Next both CPUs pass the level-113 barrier (PI_INT_PEND_MOD `0x171`, poll INT_PEND1, then
  `0x71`), the barrier seen on one CPU at LED `0x28`. `observed`.
* With PRESENT_B set and no CPU B, the PROM disables B and continues as on one CPU; the
  console differs only in PROM log messages. `observed`.
* `inferred` (LINUX `asm/sn/launch.h`, `kldir.h`): afterwards the slave waits in the PROM's
  launch loop; its launch structure is at node memory offset `0x2400` + slice × `0x200`
  (magic `0xaddbead2addbead3`); the master starts it by filling the structure and sending an
  interrupt (Hub levels 10 and 11 are CPU_ACTION_A and _B).
* slate (OBS-SLATE-0003): with two nodes of two CPUs the PROM prints "Found 2 objects (2
  hubs, 0 routers)", "Global master is /hw/module/1/slot/n2", and the BASEIO PROM "4 CPUs on
  2 nodes found"; per-CPU messages carry a node-slot-and-slice prefix such as `1A 000:`.

What the model must provide for S1 and S2: PI_CPU_NUM answered by the requesting CPU's own
port; PI_CPU_PRESENT from the configuration; both CPUs released from reset together;
coherent shared memory between them; per-slice interrupt outputs (already modeled).

`hypothesis`: both CPUs leave power-on reset at the same virtual time; Hub local reset
(below) resets both. A two-CPU run is consistent with this.

Observed with two CPUs modeled (SMP.adoc S2, 2026-10-12):

* Before memory is initialized each CPU builds a 32 KB stack in its own primary data cache
  with Index Store Tag and Index Store Data (routine at `0x1fc03b10`, called with physical
  `0x100000` and 32 KB; `sp` = cached `0x104000` on both CPUs). The stacks are private only
  because each lives in its own cache (MIPS.adoc "Lines software installs"); with memory
  standing in for the cache, B returned through a return address A had stored and ran off
  the end of the PROM.
* Both CPUs then pass the `0x24` rendezvous and the level-113 barrier; A becomes the node's
  master. The BASEIO PROM reports "2 CPUs on 1 nodes found" (slate: "4 CPUs on 2 nodes
  found"), and the one-CPU message "update_klcfg_cpuinfo: Couldn't find my structure" no
  longer appears.
* IRIX boots to `login:`; `hinv -c processor` prints "2 180 MHZ IP27 Processors" and
  `mpadmin -s` lists processors 0 and 1, both unrestricted and preemptive.

Observed on the two-CPU model (2026-10-13; `--cpu-slice` from 1 to 100,000, SMP.adoc
"Hardening the reference"):

* After the Hub local reset the PROM checks, on each CPU, that the real-time counter runs
  (routine around `0x1fc58d04`): it reads PI_RT_COUNT as microseconds (`0x1fc5ad4c`, count ×
  8 / 10), counts down 500 iterations of a two-instruction loop (`0x1fc045bc`, about 1,000
  cycles), and reads it again. If the counter has not advanced it takes a failure path
  (`0x1fc59ecc`, LED `0xa1`), the CPU stays out of the rendezvous, and the master later
  reports "peer_pled failed: Other CPU on this node died" (diag_rc 30). `observed`
  (disassembly; instruction traces of passing and failing runs).
* In the model a CPU that is ahead of the other sees device time, and so PI_RT_COUNT, held at
  the other's time for up to one slice (ADR-023). With slices up to 1,900 cycles the check
  passes on both CPUs; from 2,000 cycles it fails on B, every time. The default slice (180)
  is far inside this. `observed`. This bounds how far one CPU may run ahead of device time,
  in reference mode and in any host-parallel quantum (SMP.adoc S4).
* `hypothesis` (as before, now made exact): a local reset releases both CPUs at the same
  instant. The model resets them at one cycle count: the CPU behind is held until the other's
  cycle, as if in reset, then both reset (`Ip27Machine::reset_cpus`, `Cpu::hold_until`).
  Without this, their phase after the PROM's early local reset depended on the slice length.

=== Hub local reset

The PROM reads PI_ERR_STACK_ADDR_B early in its reset path and compares it with
`0x52737430` (ASCII "Rst0"). If they differ, it writes "Rst0" there and writes `0x81`
(PORTRESET | LOCALRESET) to NI_PORT_RESET. If they match, it continues without resetting
(`observed`). The marker must therefore survive the reset.

Model (`hypothesis` for the CPU reset kind): the reset event reinitializes the Hub's modeled
registers except PI_ERR_STACK_ADDR_A/B, and gives the CPU a cold reset.

=== Junk bus

`observed`: the PROM initializes MD_UREG0_1/MD_UREG0_0 with `0x80`, `0x7f`, `0xa0`, `0x1c`,
`0xc0`. That is the PCF8584 I²C controller's sequence: select own address, write `0x7f`,
select clock, 12 MHz / 90 kHz, enable serial output. It then reads the own address back
(LED `0x4c` I2CINIT; PRM Table 3-1 names the PCF8584). So UREG0_0 is S0 and UREG0_1 is S1.
It later sets the own address to `0x08`.

`devices::Pcf8584` models the chip from the datasheet and the public Linux driver
definitions, on a `devices::I2cBus`. As master it runs START, repeated START (S1 = `0x45`,
then the address in S0), transmission with the target's acknowledge in LRB, and reception
(each S0 read returns a byte and starts the next; the first is a dummy read; S1.ACK clear
NAKs the next byte). A byte takes nine SCL periods of virtual time. When it is not master,
its shift register latches every byte other masters send, and BB follows their STOP.
`hypothesis`: after a NAKed byte, reading S0 starts no further reception. Slave operation is
not modeled.

== System controller

The I²C bus is shared with the module's system controller, the ELSC (PROM strings: "ELSC not
responding.", "Can't talk to elsc!", "Timed out getting ELSC lock"). Sources: the IRIX-derived
Linux headers `ksys/elsc.h` and `ksys/i2c.h` (history tree v2.5.20 and v2.5.0: API, error
codes, `i2c_arb` "Timeout waiting for sysctlr arb"), the PROM's I²C driver (disassembly), and
slate's controller (read-only `sn0msc -r` reads of its NVRAM).

`observed` in the PROM's driver:

* Arbitration (`i2c_arb`, flash `0x1fc3978c`): with the bus idle, the CPU waits until S0 shows
  its token and it stays for 250 µs; it first waits for a stale copy to disappear. The token
  is `0xde + 2 × slot code + CPU slice` (slot codes 1–4 for n1–n4), or that plus 8 when the
  controller has a message for it. A transaction ends with a repeated START addressed to
  `0x7f` (byte `0xfe`) instead of a STOP.
* NVRAM (`elsc_nvram_read`, flash `0x1fc3d138`): each byte is an I²C random read of a
  24C16-style EEPROM at `0x50 | address[10:8]`, under a software lock in MD_PERF_CNT0 bit 15.
  The probe checks for magic `0x37` at `0x700` (else ELSC_ERROR_NVMAGIC, -124), bytes
  `0x700`–`0x70f` are cached, and the SN0 module number is byte `0x708`.
* The PROM addresses `0x08` and `0x20`; which is which is settled by IRIX's driver below.

`observed` in IRIX 6.5.30's controller driver (slate's unstripped `/unix`, disassembled
with its debug information; `io/elsc.c`, `io/i2c.c`, `ml/SN/SN0/sysctlr.c`):

* Commands (`elsc_command`): the node writes a packet to `0x08` (ELSC_I2C_ADDR in the
  Linux 2.4.3 `ksys/elsc.h`), then reads the answer with a repeated START addressed for
  reading. Both packets are a length byte, that many bytes of ASCII text, and a checksum byte
  that makes the packet's bytes sum to zero (mod 256); answers hold at most 96 bytes. The
  answer is `ok` or `err` with `csum`, `cmd`, `arg`, `perm`, or `pwr_state`
  (ELSC_ERROR_CMD_CHECKSUM to ELSC_ERROR_CMD_STATE, `elsc_parse`). Command texts in the
  driver: `get`, `ver`, `tas`, `dsc`, `dsp`, `pwr q`, `pwr r`, `pwr d %x`, `pwr c`, `rst`,
  `rsw`, `nic`, `hbt %d %d`.
* `0x20` is a separate port (`elsc_ust_read`, `elsc_ust_write`: one byte each way), the one
  the PROM's `ust_change` uses.
* Arbitration in the kernel's `i2c_arb` waits for token `0xe0`, or `0xe8` with the message
  flag, whatever the CPU. A command sent "only if a message waits" returns at once without
  the flag.
* Messages: `sysctlr_init` connects interrupt level 127, INT_PEND1 bit 63 (MSC_PANIC_INTR in
  the Linux `sn/intr.h`), on one CPU per module. Its handler `msc_intr` raises software level
  9 on the master CPU, whose handler `process_message` sends `get` only if a message waits
  and looks the answer up in a table of 22 messages. Among them: `pd off` "Module keyswitch
  turned OFF" and `pd remote` "Remote power-down command" (both shut the system down), `ac`
  "AC power lost", `fan fail`, `pd temp`, `nmi`, `rst` "External system reset". An empty
  answer is "MSC interrupt without message" and is ignored. `intpend1` clears each INT_PEND1
  bit (a PI_INT_PEND_MOD write) before calling its handler, and nothing in the kernel sets
  level 127 itself.
* Shutdown (`msc_shutdown`, a kernel thread): IRIX prints "module 1 MSC: Module keyswitch
  turned OFF (shutdown pending)", signals init (`sigtopid(1, SIGINT)`), and every second asks
  the controller to remove power in 8 seconds (`pwr d 8`), so that power stays on while the
  system shuts down. At the end of the shutdown `restart()` (`ml/SN/klarcs.c`) calls
  `sysctlr_power_off`, which shows "Removing power." and sends `pwr d 1`. A shutdown that the
  controller did not ask for (`shutdown -i0`) does not remove power.

Real hardware (slate, module 1): the NVRAM is 2048 bytes; `0x700`–`0x70f` hold `'7'`, "none"
(the password), zeros, the module number `0x01` at `0x708`, and `0x78` at `0x70b`; `0x000`
onward holds board-inventory text records.

Model:

* `devices::I2cEeprom` (24C16 protocol) holds the NVRAM, initially erased except for the
  `0x700` block as slate has it, with `Ip27Config::module_number` (default 1) at `0x708`
  (`initial_controller_nvram`).
* `devices::Elsc` models arbitration, the command packets, and the keyswitch.
  `hypothesis`: it offers the eight node-CPU tokens (`0xe0`–`0xe7`) in turn, 1 ms each,
  while the bus is idle, each plus 8 while a message waits; it frees the bus 100 µs after
  being addressed at `0x7f`. It answers `get` (the waiting message, or an empty answer) and
  `pwr d N` (power off in N seconds, hexadecimal; `ok`), and `err csum` to a bad checksum.
  To any other command it does not acknowledge the read address, so those commands
  (display, DIP switches, NIC, heartbeat, reset) fail with I2C_ERROR_NAK, as when no command
  was modeled, and the PROM carries on ("MSC DIP switches unavailable"). `0x20` does not
  answer.
* The keyswitch (`Ip27Machine::turn_keyswitch_off`, main's SIGPWR and monitor `off`, the
  console script's `@off`): the controller queues `pd off`, raises INT_PEND1 bit 63 on every
  node's Hub, and removes power 10 s later unless the system asks otherwise (`hypothesis`:
  the real grace time is not known; IRIX first asks about two seconds after the message).
  Removing power ends the run, which then writes the disk, NVRAM, and flash as at any other
  end.
* The NVRAM is not persisted across runs yet.
* `observed` with two nodes: the PROM's `ust_change` (`0x1fc4899c`, run on one node of a
  multi-node SN0 system) reads one byte at the command address `0x20` (`0x1fc39c14`), sets
  or clears bits 6 and 7 by a klconfig field, and writes it back (`0x1fc39bac`). The model
  does not answer, so the PROM prints "Error in ust_change: Addressed slave not responding"
  twice and continues; slate's prints nothing. Not modeled: what the `0x20` port holds is
  not known (a PCF8574-style port there was tried and withdrawn; IRIX calls it the
  controller's "ust" port).

Before this model the PROM spent 5 s waiting at I2CINIT and 21 s retrying the controller,
and module voting failed (modid -1).

== Machine type

`observed`: the PROM decides between SN0 (Origin 2000) and SN00 (Origin 200) from the word
at LBOOT + `0x90`. It is 0 in the user's image, so the PROM configures itself as an SN0 node.
That matches IP27-TARGET.adoc's Origin 2000 personality. The flash is not altered.

The node's module slot comes from MD_SLOTID_USTAT bits 2:0. `observed`: for SN0 the PROM maps
slot IDs 0–7 through the table `0xf0, 0xf0, 0x52, 0x51, 4, 3, 2, 1` (`0xf0` invalid), so node
slots n1–n4 are IDs 7–4. `Ip27Config::node_slot` (default n1, as slate's first node board)
selects it. Slot ID 0 had given "cpu in SLOT Invalid0" and `/hw/module/0/slot/n0`.

Deskside and rack modules (`observed` 2026-10-14, disassembly and a load watch on the
running PROM):

* The slot-code function (`0x1fc461fc`) returns, for SN0, the table entry for the slot ID.
  The table is the one above unless bit 0 of the word at LBOOT + `0xa8` is set (0 in the
  user's image); then it is `0xf0, 0xf0, 6, 5, 4, 3, 2, 1`.
* Codes `0x5n` are deskside ("Kego") node slots: slot ID 3 is n1 (`0x51`), slot ID 2 is n2
  (`0x52`). Codes 1–4 are rack node slots n1–n4 (IDs 7–4).
* `xbwidget_to_xtslot` (`0x1fc419cc`, named by its error message "crossbow nonzero on
  Kego") turns a Crossbow widget into an IO slot code with one of four tables (IP27.adoc
  "Crossbow"): the deskside table when the node's slot code is `0x5n` (and only for
  Crossbow 0), the SN00 table when LBOOT + `0x90` is nonzero, else the rack table of
  Crossbow 0 or 1. So the module type follows from the node's slot ID: a deskside midplane
  gives its node slots IDs 3 and 2. `inferred` for slate, whose names agree (n1 on port
  `0xa`, n2 on 9, the BaseIO on 15 named io1).
* With slot ID 3, the Hub on port `0xa`, and the BaseIO on 15 (a scratch build), the PROM's
  console output to its menu is identical to the rack layout's (n1, io1, "Global master is
  /hw/module/1/slot/n1"), and the installed IRIX boots to `login:` with identical console
  output on one and on two CPUs; the cycle counts differ slightly (`boot` 16,375,376,704
  against 16,375,106,269).
* The deskside module is the default (with the user, 2026-10-15; ADR-021): it is slate's
  chassis, the target. `--module rack` keeps the rack layout; other modules (the Origin 200,
  SN00) would be further configurations of the same machine.

== Xtalk

`xtalk::Link` is a crosstalk link's far end: PIO requests name a widget (0–15) and an offset
in its space. `xtalk::Widget` is a port's view of a widget: PIO to its space, and interrupts
(a write of a vector to its INTDEST address). The Hub's II turns PIO to IO small window w
(every widget but 1, whose window holds the Hub's own registers) into a request on its link;
with no link it fails. The Hub is itself a widget: `inferred`, its II registers are laid out
as a standard crosstalk widget (IIO_WID at `0x400000` holds WIDGET_ID, IIO_WSTAT
WIDGET_STATUS, IIO_WCR WIDGET_CONTROL), so its widget space is II offset 0 up, with 32-bit
registers in the low half of each doubleword. `observed` (xbow_sanity): an interrupt whose
address is PI_INT_PEND_MOD through the Hub's IO window (`0x01800090`) sets the level named
by its vector in PI_INT_PEND.

`observed`: INITII sets the Hub's widget number in IIO_WCR bits 3:0 from the node slot, using
the PROM's SN0 table n1 → 9, n2 → `0xa`, n3 → `0xa`, n4 → 9. The machine cables the Hub to
that Crossbow port (`hub_xbow_port`).

=== Crossbow

`devices::Xbow` (IRIX-derived Linux v2.6.12 `arch/ia64/sn/include/xtalk/xbow.h`; real
topology: see "IO slot numbering" below) answers widget 0 and forwards 8–15 to
attached widgets. Registers are 32-bit at offset 4 mod 8 (a doubleword access carries the
register in its low half, `hypothesis`).

* WIDGET_ID: part `0x0000`, manufacturer 0, bit 0 set (the JTAG IDCODE layout; the PROM
  rejects a widget ID whose LSB is 0). `hypothesis`: revision 4 (XBOW_REV_1_3). For
  revisions from 5 the PROM's xbow_sanity expects a source-ID field in the status register,
  which is not modeled.
* Per-port link registers at `0x100 + 0x40 × (port & 7)`: STATUS (and STATUS_CLR) reads
  LINKALIVE for an attached widget, AUX_STATUS reads PRESENT; control and arbitration
  registers are storage (the PROM uses port F's upper arbitration register as a lock).
* Storage: WIDGET_CONTROL, REQ_TIMEOUT, INTDEST, LLP_CFG, ARB_RELOAD, performance counters.
* LINK_RESET (`0x34` in a port's link registers) resets the widget on that port
  (`xtalk::Widget::xtalk_reset`); the Bridge's reset clears its registers, ATEs, and
  interrupt state and drives PCI RST# to its slots (`pci::Device::pci_reset`). `observed`:
  the PROM writes it for the BaseIO's port as it boots. Without it, the PROM that IRIX
  restarts into found the ISPs as IRIX left them, and IRIX's `ql_isr` then reported
  errors. `hypothesis`: reset reaches the widget and its PCI devices; ISP RISC RAM survives
  it.
* IO slot numbering (`observed`: four tables of 32-bit klconfig slot codes, indexed by
  widget − 8, in the user's PROM image at payload offset `0xd1dd0`; `0x2n` is IO slot n,
  `0x5n` and `0x0n` node slots). Deskside ("Kego", one Crossbow): 8 io4, 9 n2, `0xa` n1,
  `0xb` io2, `0xc` io6, `0xd` io5, `0xe` io3, `0xf` io1, as on slate (Kona on 8 is io4,
  MENET on 13 io5, BaseIO on 15 io1). Rack module, Crossbow 0: 8 io1, 9 n1, `0xa` n3,
  `0xb` io4, `0xc` io2, `0xd` io6, `0xe` io5, `0xf` io3; Crossbow 1 holds n2, n4, io7–io12.
  The rack tables agree with the PROM's Hub widget numbers (n1 9, n2 `0xa`, n3 `0xa`,
  n4 9). With the BaseIO on port 15 (slate's port), this machine's PROM named it io3, so
  it uses the rack table. The node's slot ID selects the deskside table ("Machine type").
  A rack module cables the BaseIO to port 8, its io1; a deskside module (the default since
  2026-10-15, slate's chassis) puts it on 15 and the node in deskside n1 on port `0xa`
  (`ip27::baseio_port`, `hub_xbow_port`; `--module rack|deskside`).
  `observed` after the move: the PROM reports "Console has moved from
  /hw/module/1/slot/io3 to /hw/module/1/slot/io1", walks SCSI on `.../io1`, and IRIX
  installed with the old topology boots unchanged.
* `observed` in xbow_sanity (whose failures name each check): INTDEST_UPPER reads its fields
  (`0xff0fffff`) with target bit 19 set; a write to a read-only register (WIDGET_ID,
  ERR_UPPER, ERR_LOWER) completes, sets REG_ACC_ERR (`0x20`) in WID_STAT, and with
  REG_ACC_IE in WIDGET_CONTROL sends an interrupt to INTDEST; WID_STAT does not clear on
  read, STAT_CLR (`0x54`) does.
* `hypothesis`: no link ever reports an error, credits and arbitration have no effect,
  counters do not count, and the NIC register (`0x74`) is not modeled.

=== Bridge

`devices::Bridge` is the BaseIO's crosstalk-to-PCI widget on Crossbow port 8 (io1), from the
IRIX-derived Linux `arch/mips/include/asm/pci/bridge.h`. Registers are 32-bit at offset 4 mod
8.

* WIDGET_ID: part `0xc002`, manufacturer `0x036`, `hypothesis` revision 4 (BRIDGE_REV_D).
* `observed` reset values (the PROM's bridge_sanity names each): status PCI_GIO_N (bit 5)
  set; WIDGET_CONTROL `0x7f0033f0` with the widget ID (the Crossbow port) in bits 3:0;
  REQ_TIMEOUT `0xfffff`; DEVICE0–7 `0x18001000`, `0x18001002`, `0x18001004`–`0x18001009`
  (ERR_LOCK_EN, PAGE_CHK_DIS, DEV_IO_MEM, and each window's PCI offset in megabytes).
* An access to an offset `bridge.h` does not define sets INT_STATUS INVLD_ADDR (bit 24; a
  write completes, a read fails). Error bits enabled in INT_ENABLE send one interrupt to the
  widget INTDEST address with INT_HOST_ERR's vector (`observed`: bridge_sanity expects it in
  PI_INT_PEND0). INT_RST_STAT clears by the BRIDGE_IRR_* groups.
* BRIDGE_NIC is a MicroLAN master (see "NICs").
* Configuration space (`0x20000 + 0x1000 × slot`, function 0 only): 32-bit accesses see the
  PCI dword's value; narrower ones address byte `offset ^ (4 − size)` (Linux
  `arch/mips/pci/ops-bridge.c`). An empty slot fails the access (a bus error), which the
  PROM's enumeration expects.
* Device windows (DEVIO0/1 2 MB at `0x200000`/`0x400000`, DEVIO2–7 1 MB from `0x600000`):
  PCI address = DEVICE(x) offset × 1 MB + offset in window, memory or I/O space by
  DEV_IO_MEM. `inferred`: with DEV_SWAP clear the window preserves byte lanes, like
  configuration space: an access narrower than 32 bits at window byte A reaches PCI byte
  A ^ (4 − size), and values pass unchanged. With DEV_SWAP set bytes keep their addresses and
  wider values arrive byte-reversed. Evidence: IP27 Linux swizzles I/O byte and halfword
  addresses by 3 and 2 with data unchanged (`asm/mach-ip27/mangle-port.h`); the PROM, with
  DEV_SWAP clear, writes 16550 register n of the IOC3 at window byte base + n, which is PCI
  byte base + (n ^ 3) where `ioc3.h` puts it (`iu_lcr` first; Linux `8250_ioc3.c` reads
  register n at `offset ^ 3`); and it polls the ISP1020's semaphore (PCI `0x0c`) at window
  byte `0x0e` and writes its HCCR (PCI `0xc0`) at `0xc2`. (Until 2026-09-27 the model had
  both the Bridge and the IOC3 inverted, which cancelled for the IOC3 and broke the ISP.)
  An access no device claims sets PCI_MST_TIMEOUT and fails.
* DMA (`pci::DmaPort` per slot): the 32-bit direct map (PCI `0x80000000` up, 2 GB) goes to
  the widget and 2 GB crosstalk block DIR_MAP names; a 64-bit PCI address names the widget in
  bits 63:60 and attributes in 59:48 (`PCI64_ATTR_*`; IP27 Linux DMA addresses are
  `masterwid << 60 | PCI64_ATTR_BAR | physical`), with the crosstalk address in 47:0.
  `hypothesis`: attributes other than VIRTUAL do not change the data. With the device's
  SWAP_DIR set, PCI bytes keep their addresses; `hypothesis`: without it DMA preserves byte
  lanes like PIO (PCI byte X is crosstalk byte X ^ 3). The PROM programs the ISPs' DEVICE
  registers without SWAP_DIR, and the ISP's little-endian IOCBs then decode correctly
  (target, LUN, CDB), which supports the hypothesis. The Crossbow routes DMA to the widget on
  the target port; the Hub delivers it to node memory (`hypothesis`: crosstalk address bits
  39:0 are the physical address, coherent and immediate).
* ATE RAM (`b_int_ate_ram`): 128 entries written as doublewords at `0x10000`; a word read at
  entry + 4 returns the high word, and at `0x11000` + 8n + 4 the low word. ATE-mapped DMA (PCI
  `0x40000000`–`0x7fffffff`, 4 KB pages or 16 KB with BRIDGE_CTRL_PAGE_SIZE) uses a valid
  entry's crosstalk address (47:12) and widget (11:8). External ATE SSRAM (`0x80000` up):
  `hypothesis` none fitted on the BaseIO; accesses complete, reads return 0 (IRIX sizes it by
  a write and read-back per size and treats a mismatch as absence).
* PCI interrupts (Linux `pci-xtalk-bridge.c`): pins INT0–7 (slot k's INTA is pin k, INTB
  generically pin k ^ 4; the BaseIO wires the IOC3's INTB, its SIO interrupts, to pin 4:
  Linux 5.10 `bridge_setup_ip27_baseio`, `int_mapping[2][1] = 4`) show in
  INT_STATUS 7:0. An enabled pin sends an interrupt to INTDEST with the vector in INT_ADDR(n)
  bits 7:0 when it rises (or when enabled while high), and with its INT_MODE bit a clear
  packet when it falls. `hypothesis`: the address is INTDEST's (INT_ADDR's host bits name the
  node, and there is one).
* External flash PROM 0 at `0xC00000` (bridge.h BRIDGE_EXTERNAL_FLASH): the BaseIO's own
  PROM, loaded from the user's `io6prom.img` with `--io6prom` (the raw promgen image, header
  first). `observed` (the IP27 PROM's flash driver, by disassembly): the port is 16 bits
  wide; commands are halfword stores at twice the word address, and identification reads
  the halfwords at 0 and 2, accepting 8-bit parts (AMD `0x01`/`0xd5`, `0xad`) and 16-bit ones
  (AMD or Fujitsu `0x22da`). `observed` (IRIX's `flash` utility reads the image byte by byte
  and, with the 16-bit part, reports the same header as on slate): the part is a 16-bit one
  in word mode (modeled as `Am29f080` in word mode with device `0x22da`, the Am29LV800BT;
  `hypothesis`: uniform 64 KB sectors, the boot sectors not modeled), so data is
  byte-linear. Writes reach it only with WIDGET_CONTROL FLASH_WR_EN (bit 31), which IRIX's
  `pcibr_map` sets when it maps the flash. With it the IP27 PROM loads the BASEIO PROM from
  flash (the build slate runs, 11:26:28, where the internal copy is 11:05:48), and `flash -i`
  reports "prom file version 6.156 is the same as current version 6.156: prom not flashed".
  Without the image the port is empty and the PROM falls back to its internal copy.
* Not modeled: FORCE_PIN/FORCE_ALWAYS, and errors other than invalid addresses and master
  aborts.

=== PCI

`pci::Device` is a PCI function 0 as the Bridge sees it: configuration dwords with byte
enables, and memory and I/O accesses it decodes through its BARs. `pci::ConfigHeader` holds a
type-0 header: identity, command, a constant status, BARs sized by their address masks, and
the interrupt line and pin.

The BaseIO population follows slate (OBS-SLATE-0001): ISP1020-family SCSI controllers in
slots 0 and 1 (`0x1077:0x1020`, class `0x0100`; `hypothesis`: revision 5, a 256-byte I/O BAR
and a 4 KB memory BAR) and the IOC3 in slot 2 (`0x10a9:0x0003`; `hypothesis`: class 0,
revision 1, one 1 MB memory BAR). `observed` (io_config_space): status reads `0x0200` for the
ISPs and `0x0280` for the IOC3 after reset.

=== IOC3

`devices::Ioc3` (register map: the IRIX-derived Linux `asm/sn/ioc3.h`).

* An ordinary little-endian PCI device: 32-bit registers hold their values in PCI byte lane
  order (through the lane-preserving window the PROM's values arrive intact: MCR `0x82104` is
  a MicroLAN reset pulse).
* UART A (16550 register n at PCI byte `0x20178 + (n ^ 3)`, `struct ioc3_uartregs`) and UART B
  (`0x20170 + (n ^ 3)`) are `devices::Uart16550`
  (PC16550D): divisor latch, FIFOs, loopback, LSR/MSR. `hypothesis`: transmission takes no
  time and interrupts are not modeled. UART A is the console (see "Console").
* MCR (`0x30`) is a MicroLAN master on the Ethernet-address NIC (see "NICs").
* SIO_CR (`0x28`) bits 22:19 are read-only arbiter status; the model's DMA moves whole
  entries between accesses, so they read ARB_DIAG_IDLE (`observed`: IRIX waits for it after "Setting rbaud to 19200").
* Every other register is traced storage (the PROM's register tests pass on storage).
* Serial DMA (Linux `ioc3.h`, `drivers/serial/ioc3_serial.c` v2.6.16): SBBR_H/L hold the ring
  buffer's PCI address (SBBR_L bit 0: 4 KB rings, else 1 KB), rings TX A, RX A, TX B, RX B;
  each port has SSCR, STPIR, STCIR, SRPIR, SRCIR, SRTR, SHADOW (port A at `0xb8`, B at
  `0xd4`). With SSCR DMA_EN and not PAUSE, the engine sends TX entries (8 bytes: 4 data, 4
  status/control; TXCB_VALID bytes go out, TXCB_INT_WHEN_DONE raises TX_EXPLICIT) from STCIR
  to STPIR, one entry per character time (`hypothesis`: 9600 baud). Received bytes, one per
  character time, collect in a four-byte packer (`ioc3_serial.c`: they "are not drained to
  memory until either there are 4 bytes available or the rx_timer expires"); a full packer
  becomes one RX entry at SRPIR (each byte RXSB_DATA_VALID | MODEM_VALID), and SRPIR's
  SRPIR_BYTE_CNT reads the bytes waiting. The RX timer starts at the first byte after
  SRCIR_ARM and runs SRTR ticks of 16 kHz (SRTR_HZ); when it runs out the packer drains as a
  partial entry and RX_TIMER latches. RX_HIGH is a level while the ring holds at least
  SSCR_RX_THRESHOLD entries (`hypothesis`). RX_DRAIN drains the packer at once.
  `observed`: the PROM's serial_dma diagnostic loops 127 four-byte TX entries back (SHADOW
  loopback and MCR LOOP) into a 127-entry RX ring and passes only with the packer: with one
  byte per entry it timed out on both ports ("Timeout on uartA dma") and the summary
  reported "IOC3 failed diag", where slate reports "ALL DIAGS PASSED" (OBS-SLATE-0003).
  `observed`: IRIX writes SRCIR with ARM and then the consumer pointer without it each time
  it reads, and drains; the model keeps the timer armed until a byte starts it (snapshots
  from before the packer load with it armed). `inferred`: entry bytes are in memory order,
  most significant byte first in each PCI dword through the lane-preserving Bridge. PAUSE
  reads back PAUSE_STATE at once (`observed`: IRIX pauses the ring and waits for it).
  SSCR_RESET empties the rings and the packer.
* SIO interrupts: SIO_IR (TX_MT a level while a TX ring is empty, `hypothesis`; other bits
  latch until written back), SIO_IES/SIO_IEC set and clear the enables; any pending enabled
  bit asserts the IOC3's INTB, Bridge pin 4. `observed`: IRIX chooses the pin by board. While
  the BaseIO's NICs carried no manufacturing record, IRIX knew the board only as a generic
  widget and enabled pin 6 (slot ^ 4). With the records it names the board BASEIO and
  enables pin 4, and an IOC3 still on pin 6 left the console without input.
* Not modeled: the parallel port and keyboard/mouse.
* Bytebus device 0 (`0x80000`) is an M48T35 timekeeper (`devices::M48t35`; Linux `ioc3.c`
  ip27_baseio_setup adds an "m48t35"): 32 KB of NVRAM with a BCD clock at `0x7ff8`, device
  byte n at PCI byte n ^ 3 (`observed`: IRIX writes the control byte at PCI `0x87ffb`). The
  clock runs on virtual time from `Ip27Config::clock_epoch` (`--date`, default 2026-01-01
  UTC); READ freezes it, WRITE loads it. The chip keeps no century; the year register
  counts from 1970 on this machine (Linux `ip27-timer.c` 2.6.12 adds 1970, and
  `rtc-m48t35.c` adds 70 to `tm_year`; `observed`: IRIX, having set its clock to 2006 from
  the root filesystem, wrote year `0x36`). With the year read as 2000-based, the 2026 epoch
  looked like 1996 to IRIX ("Check the date to make sure it is correct").
* The chip counts days on its own calendar: its leap years are those whose year register is
  a multiple of 4 (ST M48T35 datasheet), from a 1970 base 1970, 1974, ..., 2026, and not 2024
  or 2028. The model keeps the running time as seconds on that calendar since register year
  0 (for a 1970 base, Unix time until the chip's extra day in February 2026; snapshots from
  before 2026-11-03 hold such times). `--date` puts its date, in the real calendar, into the
  registers. The day of week is a counter of its own that steps with the days from what was
  written. Until 2026-11-03 the model followed the real calendar, and IRIX's correction
  (below) then moved its date a day: a machine stopped without a shutdown after 2026-02-28
  23:58 booted again to March 2 (now March 1, as the chip would give).
* The 32 KB (PROM environment, clock) persists in a host file with `--nvram FILE`, as the
  chip's battery keeps it. The file is written at the end of a run, with the running time
  latched into the clock registers. On the next power-on the clock resumes from that time
  (no virtual time passes while the machine is off) unless `--date` sets it. A snapshot's
  timekeeper state takes precedence. `observed`: without it, each power-on finds "NVRAM
  checksum is incorrect: reinitializing" and the defaults (`AutoLoad=N`), so the PROM stops
  at its menu. With a file in which `setenv AutoLoad Yes` was run once, it boots the
  installed disk without input.
* `observed` (IRIX 6.5.30 kernel, `rtodc`, by probe and disassembly of the installed
  kernel; names from slate's `/unix`): after reading the clock, IRIX reads NVRAM byte
  `0x3883` through `get_nvreg` and warns "Check the date to make sure it is correct" unless
  it is 1 or 2. The value takes part in a leap-day correction: the chip's own leap years are
  multiples of four in the register's count, which from a 1970 base are not the real ones.
  `observed` (disassembly of `rtodc` in slate's `/unix`, 2026-11-03): from the register year
  r and the month, IRIX takes an expected value X: 2 when r % 4 is 0 and the month is January
  or February, when r % 4 is 2 and the month is March or later, and when r % 4 is 3; else 1.
  When the stored byte equals X it reads the registers as a date in the real calendar; when
  it is larger it adds a day, when smaller it subtracts one, and then rewrites the clock
  (`wtodc`, which stores the byte for the time it writes). IRIX also writes the clock at a
  clean shutdown. So a clock set behind IRIX's back to a date in another phase (`--date`
  after the byte was stored in another part of the four years) reads a day off once, until
  IRIX rewrites it: `--date 2026-11-02` with the byte at 2 boots to November 3, and the next
  boot to November 2.
  `wtodc` stores the byte through `set_nvreg`. That walks the nodes and writes through
  `ioc_base(node)`, which finds the BaseIO's IOC3 at hardware-graph path
  `module/%M/slot/io1/baseio/pci/2/ioc3` (or `.../io1/MotherBoard/...`). When there is no
  such path, the write is skipped. The IOC3 was once at
  `/hw/module/1/slot/io3/xwidget/pci/2/ioc3`, and IRIX then warned on every clock read. With
  the BaseIO at io1 ("Crossbow", slot numbering) and named from its NICs ("NICs"), it is at
  `/hw/module/1/slot/io1/baseio/pci/2/ioc3` as on slate, IRIX stores the byte, and a boot
  that finds it prints no warning.

=== IOC3 Ethernet

`devices::Ioc3Ethernet` is the IOC3's Ethernet MAC, and `devices::Dp83840` its PHY. Sources:
the IRIX-derived Linux `ioc3.h` and `ioc3-eth.c` (v5.10), and the observed behavior of the
BASEIO PROM's Ethernet diagnostics (enet_ssram, enet_phy_reg, enet_nic, enet_ioc3_loop,
enet_phy_loop, enet_tw_loop, all passing) and IRIX's `ef` driver (disassembly of
`ef_ioc3reset` and `ef_recv`, names from slate's `/unix`).

* EMCR: `observed` (ef_ioc3reset): after EMCR_RST, IRIX polls EMCR for ARB_DIAG_IDLE
  (`0x00200000`) for up to a million microseconds, then reports "IOC3 reset timed out". DMA
  completes within an event here, so the arbiter always reads idle. `observed`
  (enet_ioc3_loop): software sets the ring bases before EMCR_RST and the pointers after it, so
  the reset keeps ETBR and ERBR and clears the pointers, EISR, and EIER (`hypothesis` for the
  other registers).
* SSRAM (`0x40000`–`0x7ffff`): 64K words of 16 data bits and a parity bit (bit 16). Written
  bit 17 is dropped; with EMCR_RAMPAR, a read sets bit 17 when the 17 stored bits have odd
  weight (`observed`: enet_ssram's address walk and parity patterns `0xaa55`, `0x157aa`,
  `0xbad1`, `0x1bad0`). All 128 KB are present (IRIX's `ssram_discovery` and the walk find
  no aliasing).
* MII: MICR names the PHY and register (READTRIG reads into MIDR_R; otherwise MIDR_W is
  written), completing at once (`hypothesis`). An empty address reads `0xffff`. The PHY is at
  address 31 (`observed`: the PROM addresses 31 and expects it in register 25).
* PHY: clause 22 registers with the reset values the PROM's enet_phy_reg expects
  (identifier `0x2000`/`0x5c00`, BMCR `0x3100`, BMSR `0x7809`, ANAR `0x01e1`, vendor
  registers 23 `0x8040`, 25 `0x005f`, 28 `0x0039`) and its writable bits. Loopback: BMCR
  bit 14, or a mode in register 24 bits 9:8 (`observed`: enet_tw_loop writes `0x0100` for
  "TWISTER LOOPBACK"). The cable is a machine setting (`--ethernet`): with a link partner,
  auto-negotiation completes 1.5 s (`hypothesis`) after the PHY leaves reset, at 100 Mb/s full
  duplex. IOC3 GPIO 5 is the PHY's active-low reset (`observed`: the PROM pulses GPPR[5] 0
  then 1 before enet_phy_reg and expects the link still down).
* Transmit: a ring of 128 or 512 descriptors of 128 bytes at ETBR (big-endian `cmd`,
  `bufcnt`, `p1`, `p2`, 104 bytes of data); ETPIR and ETCIR are byte offsets. The frame is the
  descriptor's data (D0V), buffer 1 (B1V), and buffer 2 (B2V), bounded by the byte count. With
  DOCHECKSUM, the complement of the ones' complement sum of the whole frame goes at CHKOFF
  (`inferred`: Linux leaves the corrections there). INTWHENDONE raises TXEXPLICIT; an empty
  ring raises TXEMPTY. The next descriptor starts after the frame's time at 100 Mb/s.
* Receive: a ring of 512 big-endian buffer addresses at ERBR; ERPIR (with ARM) offers
  buffers, and the MAC advances ERCIR. A frame goes at EMCR_RXOFF half-words into its buffer,
  then the status word and the valid word are written: V, the byte count with the FCS, and
  the ones' complement sum of frame and FCS (`observed`: enet_phy_loop's expected
  `0x8131fade`). The status is GOODPKT, the length with the FCS in bits 2:0 and 12:3
  (`observed`: enet_phy_loop expects `0x40261000` for 305 bytes), and broadcast or multicast.
  Frames from the wire are padded to 60 bytes and get their FCS. The IOC3's internal loopback
  returns the frame as sent, without FCS, with status 0 (`observed`: enet_ioc3_loop); the
  PHY's returns it like a received frame. RXTIMERINT goes up when armed; a frame delivered
  while disarmed is announced when software arms again (`hypothesis`). Frames that find no
  buffer wait, up to 64.
* Filter: the station address (EMAR_L bytes 0–3 least significant first, EMAR_H bytes 4–5),
  broadcast, the multicast hash (EHAR, bit = the bit-reversed low six bits of the
  little-endian CRC-32 of the address, Linux `ioc3_hash`), or everything with EMCR_PROMISC.
* Interrupt: EISR & EIER drive the IOC3's INTA, Bridge pin 2. EISR bits clear when written
  with 1.
* Host side: `EthernetLink` (`core/ethernet_link.hpp`) is the cable. `backends::TapLink`
  attaches to an existing Linux TAP interface the user owns; `backends::PcapLink` records the
  guest's frames in a capture file with virtual time and delivers none (deterministic). The
  MAC polls its link every 100 µs of virtual time while receiving (`hypothesis`).

=== ISP1020

`devices::Isp1020` models the QLogic controller at its host interface, from the public Linux
driver `drivers/scsi/qlogicisp.c` (2.6.12): 16-bit little-endian registers, the mailbox
handshake, RISC RAM, and each mailbox command's effect. It does not execute the downloaded
RISC firmware.

* Registers: PCI ID, CFG0 (`hypothesis`: `ISP_CFG0_1040B`, slate's QL1040B), CFG1,
  PCI_INTF_CTL (ISP_RESET self-clears and resets the RISC), PCI_INTF_STS (bit 2 RISC
  interrupt), the semaphore (bit 0), mailboxes 0–7 (the host writes an incoming set and reads
  an outgoing set), HCCR (commands in bits 15:12; `hypothesis` reads: bit 7 host interrupt
  pending, bit 5 paused, from Linux `qla1280.h`). Other registers are traced storage.
* Handshake: HCCR SET_HOST_INTR starts the command in the incoming mailboxes unless the RISC
  is paused or reset (HCCR RESET, PAUSE; RELEASE resumes); `hypothesis`: it completes 10 µs
  later, putting status in outgoing mailbox 0, setting the semaphore and the RISC interrupt.
  CLEAR_RISC_INTR clears the interrupt; the host clears the semaphore.
* ROM monitor commands: NO_OP, LOAD_RAM and DUMP_RAM (DMA, little-endian words; a refused
  transfer is HOST_INTERFACE_ERROR), EXECUTE_FIRMWARE, WRITE/READ_RAM_WORD, MAILBOX_REG_TEST
  (echo), VERIFY_CHECKSUM (`inferred` from Linux's firmware image: the length is the image's
  fourth word and that many words sum to zero). Others: INVALID_COMMAND.
* Firmware commands (after EXECUTE_FIRMWARE; `hypothesis`: QLogic's firmware as Linux uses
  it): ABOUT_FIRMWARE (`hypothesis`: the version the image's banner names; the PROM's image
  says "ISP1020 Firmware Version 02.55"), INIT_REQ/RES_QUEUE and their 64-bit forms (`0x52`,
  `0x53`: address bits 63:48 in mailbox 6, 47:32 in 7; the PROM uses these), GET/SET
  parameters (stored; target and device parameters keyed by mailbox 1), queue control and
  abort commands (accepted), STOP_FIRMWARE. A reset discards the queues and parameters.
* Queues: writing mailbox 4 (the request in-pointer) makes the firmware fetch 64-byte IOCBs
  by DMA: command (type 1, four data segments; A64 type 9, two segments with high address
  words), continuation (2; A64 `0xa`), marker (4, no response). Each command runs on the SCSI
  bus at once and posts a status entry (type 3) to the response queue: SCSI status,
  completion (COMPLETE, INCOMPLETE with state GOT_BUS only for a selection timeout, DATA
  UNDERRUN with the residual, DMA_ERROR), state flags, and automatic REQUEST SENSE data after
  CHECK CONDITION. Outgoing mailbox 4 is the request out-pointer, 5 the response in-pointer.
  ISP1040 firmware commands from Linux `qla1280.h` are accepted too: SET_RESET_DELAY (0x3a),
  SET_SYSTEM_PARAMETER (0x45), SET_FIRMWARE_FEATURES (0x4a), ENABLE_TARGET_MODE (0x55),
  SET_DATA_OVERRUN_RECOVERY (0x5a), and the A64 RAM load and dump (0x09, 0x0a).
* INTA: `hypothesis` asserted while the RISC interrupt is pending and PCI_INTF_CTL has both
  ISP_EN_INT and ISP_EN_RISC (Linux `isp1020_enable_irqs`); the IRIX kernel's driver is
  interrupt-driven (`observed`).
* Clearing the RISC interrupt (HCCR `0x7000`): `hypothesis` the interrupt stays set while the
  response queue holds entries the host has not taken (the host's out-pointer, written to
  mailbox 5, differs from the in-pointer). `observed` (register accesses, two-CPU boot,
  2026-10-13): IRIX's handler reads PCI_INTF_STS, the semaphore, and the in-pointer
  (mailbox 5), takes the responses, writes its out-pointer to mailbox 5, clears the RISC
  interrupt, and reads PCI_INTF_STS again for more. A command another CPU queued completed
  between its read of the in-pointer and the clear; when the clear dropped the interrupt
  regardless, that response was never taken, and IRIX reported "ql0: Command timeout" 81 s
  later and reset the chip. With one CPU it also happens (a completion inside the handler,
  which then waited for the next interrupt): the `fs` benchmark keeps its output and cycle
  count, and ends at another PC.
+
Evidence sought for the clear rule (2026-10-13). No public document defines it: bitsavers'
QLogic directory holds the ISP1020B/1040B and ISP1040B data sheets (83140-580-01B,
-01C), four pages each with no firmware interface. Public drivers order the handler
differently: OpenBSD `qlw.c` (1.48) clears the interrupt, then reads the in-pointer, which
needs no rule because a later response raises a new interrupt; Linux `qlogicisp.c` reads the
in-pointer, then clears, and IRIX clears last, both of which lose a response posted between
the read and the clear unless the chip keeps the interrupt (this rule) or the firmware does
not post while the interrupt is pending (the alternative, which would show as mailbox 5 not
advancing while PCI_INTF_STS bit 2 is set). Only the chip running IRIX's firmware can decide
between them; the experiment is in SMP.adoc "Open questions for slate".
* Not modeled: a full response queue, asynchronous events, transfer time.

=== SCSI

`scsi::Bus` holds targets by ID; a target executes a CDB for a LUN and drives the data phases
through the initiator's `scsi::DataPhase`. Host storage is a `BlockStore` (backend
`backends::FileBlockStore`), separate from the guest-visible device.

* `scsi::CdRom` at bus 0 ID 6 (slate's position): slate's drive identity, TOSHIBA CD-ROM
  XM-6201TA 1037 (OBS-SLATE-0002). `hypothesis`: 512-byte logical blocks at power-on, the
  sector size in the SGI volume headers of IRIX media (MODE SELECT may choose 2048).
  `--cdrom FILE`.
* `scsi::Disk` at bus 0 ID 1 (slate's system disk position; sash installs to `dksc(0,1,*)`):
  identity IBM HUS103036FL3800 RPQR (OBS-SLATE-0002), 512-byte blocks, `hypothesis` geometry
  16 heads × 64 sectors in mode pages 3 and 4. `--disk FILE` (an existing image, written in
  place; `truncate -s 9G` makes a blank one).
* A disc change makes the CD-ROM's next command (other than INQUIRY and REQUEST SENSE) fail
  with UNIT ATTENTION, NOT READY TO READY CHANGE (06/28/00).
* Eject. `observed` (2026-11-04, `--trace scsi`): IRIX 6.5.30's `eject` sends INQUIRY twice,
  PREVENT ALLOW MEDIUM REMOVAL (allow), and then 0xc4, Toshiba's vendor-unique caddy eject
  (OP_VT_EJECT in the public xmcd CD player's `libdi_d/vu_tosh.c`, also in WorkMan's
  `drv_toshiba.c`: a 10-byte CDB, byte 1 bit 0 immediate, no data), never START STOP UNIT.
  Before the drive answered 0xc4 it failed with ILLEGAL REQUEST and `eject` printed "Unable to
  eject. Try hardware eject." The drive now ejects on 0xc4 and on START STOP UNIT with LoEj
  and not Start (SCSI-2 9.2.17), and leaves the drive empty (NOT READY, MEDIUM NOT PRESENT).
  While PREVENT ALLOW MEDIUM REMOVAL has removal prevented, both fail with ILLEGAL REQUEST,
  MEDIUM REMOVAL PREVENTED (53/02; `hypothesis` for 0xc4). `hypothesis`: a caddy drive cannot
  load, so LoEj with Start changes nothing. Checked with IRIX: `eject` succeeds and `mediad`
  unmounts `/CDROM`; a disc inserted afterwards (monitor `cdrom FILE`) is mounted again, and
  ejects again.
* INQUIRY with EVPD set, or with a page code and EVPD clear, fails on both targets with
  ILLEGAL REQUEST, INVALID FIELD IN CDB (24/00): vital product data is optional (SCSI-2
  8.2.5) and none is modeled. IRIX does not ask for it.
* Not modeled, and failing with ILLEGAL REQUEST when IRIX sends them to the CD-ROM: READ TOC
  (0x43), GET CONFIGURATION (0x46), and the vendor-unique 0xc9 (not in xmcd's Toshiba
  table).
* Not modeled: disconnection, tagged queuing, transfer timing, unit attention after reset.

`observed` with the user's PROM and IRIX 6.5.30 media: the BASEIO PROM walks both adapters
with INQUIRY ("1+ … 6+ … = 2 device(s)"), the install menu offers "Local SCSI CD-ROM drive 6,
on controller 0", reads the CD's volume header, and loads `sash64` (block 38033). From the
Command Monitor, `boot -f dksc(0,6,8)sash64 dksc(0,6,7)stand/fx.64 --x` runs IRIX's fx, which
labels the blank disk (writes blocks 0 and 2).

=== NICs

Board NICs are Dallas 1-Wire add-only memories ("Number In a Can"). `devices::OneWireBus`
resolves each time slot as a wired-AND of the master and every device; `devices::Nic` is a
DS2502-family part (ROM ID with Dallas CRC-8; Read, Match, Skip, and Search ROM; Read Memory,
Read Data/Generate CRC, Read Status; 128 bytes in four pages, 8 status bytes). Sources: the
DS2502 datasheet, application note 937, and Linux `drivers/net/ioc3-eth.c` (2.4.20: slot
timings, the search algorithm, family `0x91` for SGI's parts).

MicroLAN masters (Hub MD_MLAN_CTL, BRIDGE_NIC, IOC3 MCR) share the MCR encoding of the
IRIX-derived Linux `asm-ia64/sn/nic.h` (`MCR_PACK(pulse, sample)`, DONE bit 1, DATA bit 0). A
pulse of 400 µs or more is a reset (a present device pulls the sampled line low), up to 15 µs a
read or write-1 slot, longer a write-0 slot, 0 a wait.

* Manufacturing record (`observed`: IRIX 6.5.30 `nic_mfg_next` and `nic_read_mfg`, by
  disassembly; names from slate's `/unix`). IRIX reads it from parts of family `0x09`
  (DS2502: pages 0 and 1, following status-byte redirection) or `0x0b` (DS2505, read with
  CRC-16 checks). Other families yield only a laser serial. Each 32-byte page is read with
  Read Memory (for a DS2502, after the address CRC-8) and must pass a Dallas CRC-16 over all
  32 bytes with residue `0xb001`: bytes 30–31 hold the complemented CRC of bytes 0–29, low
  byte first (`devices::dallas_crc16`). `observed`: without it, the PROM with family `0x09`
  parts never reached its console (LED `0x22`, then `0x80` blinking once a second). With page 0 = A and page 1 = B,
  the record is parsed when A[0] is 1: A[1..10] serial (barcode), A[11..29] then B[0..5]
  part number, B[6..9] revision, B[10] group, B[11..14] capability, B[15] variety, B[16..29]
  name. IRIX formats it as
  `Part:...;Name:...;Serial:...;Revision:...;Group:..;Capability:..;Variety:..;Laser:...;`
  (`observed`, `nic_read_mfg`'s text copy; the IP27 PROM's copy is the same): each piece
  drops spaces and `0xff`, shows other control and high bytes as `.` and `:` or `;` as `?`,
  and a piece left with no text is written as one space. The part number is two pieces
  (A[11..29], then B[0..5]), so a part number in page A alone reads with a trailing space,
  and an empty field reads as two spaces. The PROM prints the same fields ("Found family
  0x0b Mfg. Board data", "Serial #", "Part #", "Revision", "Group/Capability/Variety", "Part
  Name"). `ip27::board_nic_memory` builds the record. Text is padded with spaces
  (`observed`: slate's `hinv -mvv` shows spaces after a barcode, where NUL padding shows as
  dots). slate's part numbers read with no trailing space (`hinv` prints `part %12s`:
  "030-1066-002 rev", where a trailing space gives two), so page B holds text: the part
  number ends the 25-character field (`hypothesis`: right-justified; any split with text in
  page B reads the same). `hypothesis`: the other bytes are unprogrammed.
* Why the text matters (`observed`, 2026-11-03): ESP's `configmon` stores each board's
  fields in its database (MySQL 3.23, which drops trailing spaces) and compares them with
  the live ones at every boot. With the trailing spaces every boot found the boards changed,
  and the replace path (`replace_hwcomponent`, then a tree copy that reads a freed
  component; core at `alloc_block`, by disassembly of the core) dumped core from the second
  boot of a system on. With the part numbers right-justified and a part number and revision
  on the IP27 board, `configmon -u` reports "Nothing to do!" and no core appears, also
  across a change from one CPU to two; a system installed before the change dumps core once,
  on its first boot after it, while its database is brought up to date.
* The BaseIO's NIC bus (BRIDGE_NIC) holds its two board NICs as DS2502 parts with slate's
  records (OBS-SLATE-0004) and synthetic serials: MIO (laser `0x1`, barcode UVX001,
  030-0880-003 rev C) and BASEIO (laser `0x2`, UVX002, 030-0734-003 rev A), group `ff`,
  capability `ffffffff`, variety `ff`. The PROM and IRIX only display the serials. `observed`: with the parts present the PROM treats the board as a BaseIO.
  With the records it prints "using BaseIO nic" where it had printed "no BaseIO, using
  random value".
  With family `0x91` and no record, the PROM's klconfig board had `brd_nic` all ones and no
  name, and IRIX named the board `xwidget`.
* The IOC3's NIC bus holds the Ethernet address NIC: `Ip27Config::ethernet_address`
  (`hypothesis` default `08:00:69:0e:17:01`, SGI's OUI; not slate's) stored so that Linux's
  reader finds it (address byte j at memory byte 11 − j).
* Each node board's MicroLAN (Hub MD_MLAN_CTL, `Node::mlan`) holds its board NIC: a DS2502
  with a record named "IP27" (`hypothesis`, after slate's "IP31" node boards; the real
  part number is unknown: a synthetic 030-9999-001 rev A, as slate's node boards have a part
  number and revision and blank ones read as spaces), barcode UVX005 for n1 and UVX006 for n2, laser
  `0x5` and `0x6`. In a deskside module n1's bus also holds the module's NICs, as slate's
  (OBS-SLATE-0004): MODULEID (barcode K0000001, no part number, laser `0x3`) and the
  midplane 4P1G5_MPLN (030-1066-002 rev K, barcode UVX004, laser `0x4`); serials are
  synthetic. slate's IP31 boards also carry a processor-module NIC (IP31PIMMR12KS); an
  IP27 board has no PIMM (`hypothesis`). `observed`: with the board NIC the PROM no longer
  prints "using BaseIO nic" (its fallback, "Hub NIC broken; using BaseIO nic", which gave
  both Hubs of a two-node machine the BaseIO's NIC as their identity), and two-node
  discovery still elects n2, as slate does.

=== PIO errors

A CPU access to a crosstalk small window that no widget answers (an absent widget; a
Bridge master abort) is a bus error for a read and a PIO error the requesting CPU's own Hub
records in PI_ERR_STATUS0 of its slice (LINUX sn0/hubpi.h): VALID (63), the address bits
39:3 at 61:25, and the error type, PI_ERR_RD_PRERR or PI_ERR_WR_PWERR (`hypothesis` for the
type; CMD, SUPPL, and the T5 request number read zero). The requester, not the node the
address reaches, records it: the machine maps each node's view of every node's small
windows per CPU slice (`Ip27Machine::PioErrorWindow`).

* `observed` (disassembly of the PROM and of IRIX, 2026-10-30): the PROM clears ERR_STATUS0
  (a write to ERR_STATUS0_A_RCLR) and reads `0x9200000002400208`, widget 2's small window,
  which no widget answers; a boot-time IRIX check then deems a CPU's firmware current
  only if its ERR_STATUS0 is valid with address field `0x480041` (that address), and
  prints "Some CPUs have old firmware. Please update node board flash proms." otherwise.
  slate's IRIX does not print it (OBS-SLATE-0003).
* `observed`: right after that check IRIX writes PI_ERR_INT_PEND and zero to
  ERR_STATUS1_A/B_RCLR, and after each address probe (`_badaddr_val`, the BaseIO Bridge's
  PCI configuration space slot by slot) it reads ERR_STATUS0 and 1 and writes
  ERR_STATUS1_A_RCLR. So a write to any of a slice's status addresses clears the slice's
  error (`hypothesis`: status 0 and 1 are one error); a read of ERR_STATUS0's clear-on-read
  form clears it too. Measured: without IRIX's clear, its probe handler blamed the PROM's
  signature for the next probe's bus error and panicked ("Partial read error").
* Not modeled: OVERRUN and the PI error stack in memory that a second error spools to; the
  first error stays until cleared (with OVERRUN set and no stack, IRIX panicked "Invalid RRB
  in error stack"); PI_ERR_INT_PEND bits for these errors; ERR_STATUS1; errors through the
  big windows.

=== Hardware inventory

The BASEIO PROM keeps a hardware inventory in the BaseIO NVRAM ("Checking hardware
inventory"), observed from its code (disassembly of the running BASEIO PROM, 2026-10-29):

* A 24-byte header at NVRAM offset `0x14bf` (5311), behind a validity byte `0x4a` at `0x4bd`
  (1213); bytes 8-15 of the header are the table's ID.
* The ID is the MODULEID NIC's laser serial: the PROM walks klconfig for the IP27 board,
  takes its Hub's manufacturing NIC text, finds "MODULEID" (else "MPLN", the midplane) and
  parses the hex after the next "Laser:". On an SN00 (the flash block's `mach_type`, offset
  `0x90` of `ip27config_t`, LINUX `sn0/ip27config.h`, is 1) the ID is 1.
* A header whose ID is 0 on an SN0 (`mach_type` 0) prints "Warning: Inventory table ID
  value is 0. Check Midplane NIC" and is rewritten with the ID ("Writing N records..
  DONE", "Updated new configuration"). So the warning appears once, on the first boot
  after the NVRAM was created without a MODULEID NIC (as the fixtures' were, before S5.2):
  `observed`, the next boot with the same NVRAM is clean. A different configuration
  reports its new boards and components instead ("Found new or re-enabled component CPU
  B", "Found a new IP27 board in module 1, slot n2") and asks for the Command Monitor's
  `update`, which writes the records (`observed`; slate's capture shows the same request
  for its graphics and MENET boards).

=== Console

The guest console is the IOC3's UART A. `backends::ScriptedConsole` writes its output to
standard output and types each `--console LINE` when the guest polls for input after a
prompt: output ending in `> `, `] `, `? `, `: `, `) `, or a shell prompt (`# `, `$ `, `% `)
followed by 200 input polls without more
output, or any output followed by 20000 (`hypothesis`: then it is waiting; `observed`: the
BASEIO PROM drains typeahead just before its "press <enter>" prompts, so a line released on
the first poll is lost). On a run resumed from a snapshot the
first line is typed at the first input poll. A script line `@cdrom FILE` is not typed: when
its turn comes the disc changes (the CD-ROM then reports UNIT ATTENTION) and the next line
follows; `@off` turns the keyswitch off in the same way (System controller). `--stop-at-prompt` ends the run when the script is used up and the guest waits at a
prompt, so snapshots land at the next question. The UART takes an input byte when software reads LSR or RBR with
its receiver empty, so input depends only on guest behavior: runs stay deterministic.

`--interactive` hands the console to the user once the script is used up
(`backends::TerminalInput`). Standard input is read without blocking, at most once per
millisecond of host time, and a terminal is put in raw input mode, so Ctrl-C and other
control keys reach the guest. Ctrl-] ends the run as a signal does: the snapshot, flash,
NVRAM, and disk are still written, and the terminal is restored. Output is flushed before
each read, so prompts without a newline appear. Interactive runs are not deterministic;
checkpoints and tests use scripts.

=== Diagnostics

`ultraviolent --probe PC` traces a0–a3, ra, and v0 whenever execution reaches `PC`. It is
the cheap way to see a PROM routine's arguments without an instruction trace.

The PROM prints messages before any console device exists; its output vector discards them.
To read them, probe the PROM's character output routine and decode a0. In the user's image
it is at `0xc00000001fc32740`:

[source,shell]
----
build/release/ultraviolent --machine ip27 --prom assets/firmware/ip27prom.img \
    --cycles N --probe 0xc00000001fc32740 --trace cpu |
  awk '/probe/ {print $6}' |
  python3 -c 'import sys; print("".join(chr(int(x, 16) & 0xff) for x in sys.stdin.read().split()))'
----

This observes only; the address is specific to that image and is never used by the model.

=== Snapshots

`ultraviolent --save-state FILE` writes the machine state when the run ends, and
`--load-state FILE` resumes from one. The state is a `StateImage` of named fields (CPU, TLB,
FPU, scheduler events, Hub, PCF8584, and memory as sparse 64 KiB pages). Loading checks the
memory size, processor clock, and an FNV-1a hash of the flash, and fails on a mismatch. A
resumed run is bit-identical to an uninterrupted one (`ip27.snapshot_resumes_exactly`).
A two-CPU snapshot adds `machine.cpus` and CPU B's fields under `slice_b.`; a two-node one
adds `machine.nodes` and the second node's CPUs, Hub, PCF8584, flash, directory, and memory
under `node1.` (`ip27.two_nodes.snapshot`). A machine of another shape refuses it.

Snapshots only shorten exploration (for example, skipping the 26 s ELSC wait). A checkpoint
in STATUS.adoc is established only by a run from power-on.
