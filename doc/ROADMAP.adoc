= Roadmap

The roadmap is capability-gated, not calendar-gated.

No milestone is complete because code exists. It is complete when its acceptance criteria
are reproducible.

== M0 - Clean core boots itself

Goal: establish the repository and deterministic execution substrate.

Deliverables:

* C++23 project builds with Clang and GCC;
* CMake/Ninja presets;
* unit-test harness;
* virtual clock;
* event queue/scheduler;
* typed addresses;
* RAM/ROM/MMIO mapping;
* interrupt-line primitive;
* reset model;
* logging/trace categories.

Acceptance:

----
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
----

all succeed on the reference Debian host, including sanitizer presets.

== M1 - Reference R1x000 interpreter

Goal: correct architectural CPU execution independent of IP27.

Implement and test:

* integer registers and PC;
* MIPS III/IV instructions required by R10000;
* branch/delay-slot semantics;
* exceptions and precise EPC/BD behavior;
* CP0;
* TLB;
* endian behavior;
* LL/SC semantics;
* FPU architecture required by PROM/IRIX.

Acceptance:

* synthetic instruction tests pass;
* exception/TLB tests pass;
* execution has no dependency on `Ip27Machine`.

== M2 - Minimal IP27 reset machine

Goal: compose one legitimate machine.

Implement:

* one CPU;
* RAM;
* Hub reset-visible state;
* PROM mapping;
* machine reset sequence;
* serial path required to observe firmware.

Acceptance:

* original PROM begins executing from reset;
* execution is deterministic;
* no PC-specific special cases.

== M3 - Stable PROM environment

Goal: reach a repeatable usable PROM environment.

Implement the hardware behavior PROM actually probes:

* Hub PI/MD/IIO portions as required;
* Xtalk/XIO topology seam;
* XBOW topology sufficient for the selected system;
* Bridge discovery/configuration;
* IOC3 serial;
* NVRAM/flash behavior required by PROM.

Acceptance:

* PROM reaches a stable command environment;
* reset/reboot is repeatable;
* firmware inventory is internally consistent;
* unknown accesses are accounted for or documented.

== M4 - Storage path

Goal: load software from original media.

Implement:

* PCI transactions needed by IO6;
* ISP1020 behavior;
* SCSI bus;
* disk target;
* CD-ROM target;
* DMA;
* completion/interrupt scheduling.

Acceptance:

* PROM discovers expected SCSI devices;
* standalone loader can read original installation media;
* a kernel image is loaded without modifying media or firmware.

== M5 - IRIX kernel

Goal: move from firmware correctness into OS correctness.

Focus:

* CP0/TLB/exception edge cases;
* timer behavior;
* interrupts;
* DMA ordering;
* memory aliases/cache-control architectural effects;
* hardware graph discovery.

Acceptance:

* unmodified IRIX kernel reaches progressively documented checkpoints;
* early VM initialization succeeds;
* device discovery succeeds;
* root/install filesystem mounts.

== M6 - Installation

Goal: install IRIX using the original installation workflow.

Acceptance:

* installation runs from user-supplied IRIX media;
* target virtual disk is partitioned/labeled by IRIX;
* filesystems are created by IRIX;
* installation completes without host-side filesystem construction;
* the installed disk cold-boots.

== M7 - Multiuser system

Goal: make the installed system a usable IRIX host.

Acceptance:

* init reaches normal multiuser operation;
* serial login succeeds;
* filesystem writes persist across clean shutdown/reboot;
* common shell/process/filesystem smoke tests pass.

== M8 - Ethernet

Goal: place the guest on a real host network.

Implement:

* guest-visible IOC3 Ethernet behavior needed by IRIX;
* DMA descriptors and interrupts;
* Ethernet backend interface;
* Linux TAP backend;
* deterministic packet injection hooks for tests.

Acceptance:

* IRIX configures the interface through its original driver;
* host and guest can exchange IP traffic;
* guest can reach another system through a Linux bridge/TAP topology.

== RC-IP27

RC-IP27 is defined in `RC-IP27.adoc`.

The release gate is remote network login to unmodified installed IRIX.

== After RC-IP27

Only after RC-IP27:

=== Performance baseline

* profile interpreter;
* establish benchmark corpus;
* remove accidental bottlenecks;
* design Ultraviolent IR.

=== JIT

Designed in `JIT.adoc`: a MIPS execution engine parameterized by the processor personality
(ADR-022), milestones J0 (processor-personality boundary and single-source semantics builder)
through J6 (block linking, only if profiling asks for it).

* differential execution against interpreter;
* tier-1 native code from the one source of semantics;
* optional optimizing tier later;
* keep interpreter permanently.

=== Usable VM

Agreed with the user 2026-11-02, after the tier-1 speed work: someone with their own PROM
image and IRIX media can install IRIX, boot it, and use it day to day without reading the
development history.

* the guest's clock keeps real time and an idle guest leaves the host mostly idle (host
  pacing, `--realtime`; guest-visible behavior unchanged);
* a soak: hours of IRIX under load (builds, file churn, network) without failure;
* a user's quickstart: what to supply, install, boot, network, shut down;
* installation from CD-ROM in one cold run, scripted;
* known limits written down (serial console only, one system disk, the two-node `ust_change`
  message);
* then a release, if the user wants one (at RC-IP27 they chose no tag).

=== SMP IP27

Target (ADR-021): the topology of the reference machine `slate`, one deskside module with two
node boards of two CPUs each, built from R10000s first and as IP31 / R12000 second.

* two CPUs per node;
* deterministic reference scheduling;
* correct guest memory ordering and atomic behavior.

=== Multi-node Origin 2000

* the two-node link of the ADR-021 target, as read from `slate`, before any larger
  configuration;
* routers/NUMAlink generation appropriate to IP27;
* distributed memory topology;
* guest-visible directory/coherence semantics;
* partition/topology work as required.

=== IP35 / Origin 3000 family

IP35 is a new machine personality, not an enlarged IP27.

Add Bedrock/C-brick/R-brick/I-brick/NUMAlink 3 concepts without modifying the general CPU,
scheduler, backend, or tracing architecture merely to accommodate the new machine.

=== Workstation personalities

Add workstation chipsets and graphics only after the server reference architecture is
proven.

=== Graphics acceleration

Potential backends:

----
faithful frontend -> software
                  -> Vulkan
                  -> FPGA
----

High-level GL interception may exist as an optional acceleration mode, but must not be
required for the faithful machine path.

=== Multi-machine orchestration

Support many independent Ultraviolent instances on Linux/Proxmox, shared virtual
networking, snapshots, and eventually specialized virtual interconnect services.
