= Multiprocessor IP27

Status: accepted with the user (2026-10-12; ADR-023). S0-S3 are done (2026-10-12), and the
two-CPU reference was then hardened (2026-10-13; "Progress"). Next, chosen by the user
(2026-10-13): S5, the second node, still on one host thread, before S4 (host-parallel); its
plan is "S5: the second node (plan)".

This is the plan for ADR-021's target, one deskside module with two IP27 nodes of two CPUs
each, starting with the smallest new piece: a second CPU on one node's Hub. It follows the
shape of `IR.adoc` and `JIT.adoc`: what is known, what must be observed before modeling, the
design, and stages with acceptance gates. The review questions are at the end.

== Goal and scope

The user's goal (2026-10-10): each guest CPU at its nominal clock in virtual time, and
host-parallel in fast mode (VISION "Fast mode", JIT.adoc "Toward host-parallel vCPUs").
Reference mode stays single-threaded and deterministic, and remains the oracle.

In scope, in order: two CPUs on one Hub (slices A and B) in reference mode; the same on the
fast engines on one host thread; the second node on one host thread; then host-parallel CPUs
(the order changed with the user, 2026-10-13; first it put host-parallel CPUs before the
second node). The second node,
the module's interconnect, and the IP31 / R12000 variant each get their own plan once the
evidence for them is read from `slate` (ADR-021 "Not decided here").

Out of scope: more than two nodes, routers, partitioning, graphics (ADR-012).

The single-CPU configuration stays the default until the two-CPU one passes its gates, and its
benchmark digests and same-cycle snapshots must not change.

== What is known

=== The PROM is written for both slices

`observed` (IMAGE, disassembly of the reset vector at `0x1fc00800`): the first thing the
PROM does after setting Status is read PI_CPU_NUM (HSPEC IO `0x9200000001000020`), scale
it by 8 to select its slice's LED register, and write LED `0x5e`. A little later it reads
PI_CPU_NUM again and, if it is nonzero, spins 128 iterations before continuing, which staggers
CPU B behind CPU A. Both CPUs therefore run the same reset code from the same vector, and
the Hub's answer to PI_CPU_NUM is what tells them apart.

`inferred` (LINUX `asm/sn/launch.h`, IRIX-derived, "Copyright (C) 1992 - 1997, 2000 Silicon
Graphics"): after reset one CPU per node becomes the master and the others wait in a PROM
"slave loop". Each node's memory holds an array of launch structures, one per CPU, at a
fixed place: magic `0xaddbead2addbead3`, busy, the call address and its ones' complement, one
parameter, stack and gp, and three BEV exception handler addresses (`0x100` bytes each). The
master fills a slave's structure and then sends that slave an interrupt; the slave checks
the complement, clears it, calls the routine, and returns to the loop. One interrupt level
is used per local CPU. The PROM exports `LAUNCH_SLAVE`, `WAIT`, `POLL`, and `LOOP` entry
points to the kernel.

=== The Hub already has per-slice state

The model (`hub.cpp`) already keeps per-slice INT_MASK0/1, RT compare, RT and profiling
pending and enable bits, CPU enable, PI_ERR_STACK_ADDR, and LEDs, and wires each slice's
interrupt outputs with `Hub::connect_cpu(slice, ...)`. What is single-CPU today:
PI_CPU_NUM always answers slice A (`requesting_slice = 0`), and PI_CPU_PRESENT_B reads 0
(`cpu_present = {1, 0}`, labeled `hypothesis`).

=== IRIX's view

`inferred` (LINUX `asm/sn/intr.h`): Hub interrupt levels 10 and 11 are CPU_ACTION_A and
CPU_ACTION_B, the inter-processor "action" interrupts; levels 45-52 are IP27_INTR_0-7, the
low ones reserved for the PROM. An IPI is therefore an ordinary PI_INT_PEND_MOD write of a
level that only the target slice's INT_MASK enables, which the Hub model already routes.
`observed` (symbol names in slate's `/unix`): `sendintr`, `cpuaction`, `bootstrap`, `cboot`,
`allowboot`, `cpu_enabled`, `cpu_unenable`, the NMI save routines, `slave_ksa`.

=== slate

Two nodes of IP31 / R12000 at 400 MHz (OBS-SLATE-0001, -0004); the PROM there is 6.156,
the same version as the user's image. Its console capture of a healthy cold boot
(OBS-SLATE-0003) is the reference for what the PROMs print with four CPUs.

== Design

=== Machine and configuration

`Ip27Machine` owns its CPUs (two `mips::Cpu`, slice-indexed, with their engines and code
memory per CPU). A configuration value, `--cpus 1|2` (per node), selects one or two; the
Hub's PI_CPU_PRESENT bits follow the configuration rather than a constant. The machine owns
which CPU is in which slice; nothing in `arch/mips` learns about slices or Hubs.

=== Who is asking: the requester

PI_CPU_NUM, and later every per-processor behavior of the PI, depend on which processor
issued the access. Decided (ADR-023): structurally, a Hub port per slice, as on the hardware,
where each processor has its own SysAD connection into the PI.

Built (S1, S2): `Hub::port(slice)`; one shared `AddressSpace` whose Hub window is mapped
per requester (`map_ports`), and each `Cpu` is built with its requester number (A 0, B 1).
Everything else in the space (memory, flash, crosstalk) is the same mapping for both. One
space rather than one per CPU, because the space also counts stores to code frames and
mapping changes, which both CPUs must see.

=== Time and scheduling (the main decision)

Each CPU has its own cycle count and its own virtual time, `time_at(cycles, clock)`, as the
single CPU has now. Devices and the scheduler see one virtual time. The rule today
(IP27.adoc "Machine loop and time") is that the scheduler is brought up to the accessing
CPU's time immediately before a device access. With two CPUs whose times differ, a device
access by the CPU that is behind would move the scheduler backwards, so a rule is needed.

Built (S2, `Ip27Machine::run_two`; ADR-023):

* **Lowest time first, in slices.** The machine runs the CPU with fewer completed cycles
  (slice A on a tie) until it is `cpu_slice` cycles ahead of the other, then switches. A
  slice ends only there (or at a stop): when an event falls due the engine returns, the
  event runs, and the same CPU continues its slice; stepping under `--probe` or `--trace
  cpu` gives the same order. The order depends only on cycle counts: deterministic, and the
  same observed or not (fixed 2026-10-13; before, a slice also ended where the engine
  returned, so tracing a run changed it).
* **Virtual time is the CPU furthest behind.** The scheduler is brought up to it before
  every device access and when an event is due. While the running CPU is ahead of the other,
  virtual time is the other's, so an event later than that cannot fall due in the slice.
  Virtual time never goes backwards, and no CPU's cycle count changes inside an instruction.
* Skew between the CPUs, and between a CPU's own Count and device time, is at most one
  slice. `--cpu-slice 1` alternates every cycle, the strict setting; the default is 180
  cycles (1 µs at 180 MHz, about one 800 ns RTC tick, far below IRIX's 1 ms clock tick).
* **The guest bounds the slice.** The PROM checks that PI_RT_COUNT advances across a loop of
  about 1,000 cycles; the CPU that is ahead sees it held for up to a slice, so from 2,000
  cycles the check fails on CPU B and the master reports "Other CPU on this node died". Up
  to 1,900 it passes (IP27.adoc "Two CPUs on a Hub"). IRIX's own results (two-CPU `cpu2`
  and `mix2` from a root shell) are the same from 1 to 100,000 cycles.
* `--cycles N` runs until both CPUs have completed N more cycles.

The guest cannot rely on finer ordering than the real machine guarantees: two CPUs on a Hub
see each other's stores in an order MIPS IV only constrains with SYNC and LL/SC.

=== Memory, LL/SC, SYNC

Built (S2): `mips::Coherence`, shared by the CPUs of a machine with two; a one-CPU machine
has none, and its CPU behaves exactly as before.

* Memory is one shared array; each CPU keeps its own host page caches. Decoded blocks are
  validated by per-frame generations held in the shared memory, so a store by either CPU to
  code invalidates the other's blocks, provided the store reaches the bus: when a CPU claims
  a frame for decoded code, the other CPU drops its writable host pages at its next engine
  entry or bus access.
* LL/SC: an LL reserves one 128-byte line (the secondary block size, `hypothesis`); a store
  by the other CPU anywhere in the line breaks it, and SC succeeds only with LLbit set and
  the reservation intact. Taking a reservation makes the other CPU drop its writable host
  pages, and a CPU never caches a writable page for a frame where the other holds one, so
  every such store goes through the slow path, where it is checked. ERET releases the
  reservation with LLbit. `hypothesis`: DMA does not break reservations (unchanged from one
  CPU; no observation needs it).
* SYNC: a no-op in reference mode (one CPU runs at a time); a host fence in host-parallel
  mode.
* Caches: refills are not modeled and memory stands for every line, as with one CPU, except
  primary data lines software installs with Index Store Tag, which hold that CPU's private
  data (MIPS.adoc "Lines software installs"). The PROM's first stack lives there on each CPU
  at the same physical address.
* The instruction cache is not coherent with stores (JIT.adoc): guest software synchronizes
  explicitly before running modified code, and each CPU's decoded blocks follow the frame
  generations above.

=== Interrupts

IPIs need no new mechanism: a PI_INT_PEND_MOD write sets the level, and each slice's mask
routes it (`Hub::update_interrupts` already does this for both slices). What is new is that
slice B's outputs reach a CPU. The interrupt is seen by the target CPU at its next
instruction boundary in its own time, within the slice rule above.

=== Reset

Power-on and Hub local reset (NI_PORT_RESET LOCALRESET, IP27.adoc "Hub local reset") reset
both CPUs; warm reset is per the existing model. `hypothesis`: both leave reset at the same
instant. Built (2026-10-13): the CPU behind is held until the other's cycle count
(`Cpu::hold_until`), then both reset, so they start in the same phase whatever the slice.
A reboot from IRIX (`init 6`) resets both, and the PROM and IRIX find both again
(`reboot2`).

=== Snapshots

Built (S2): a two-CPU snapshot adds `machine.cpus`, CPU B's state under the prefix
`slice_b.` (`Cpu::save_state` with a key prefix), and the reservations. A one-CPU snapshot
keeps its format, and a snapshot loads only into a machine with the same number of CPUs.

=== Tracing

Every CPU-scoped trace record and `--probe` hit names its slice. The flight recorder keeps
per-CPU PCs.

=== Host-parallel (later stage, sketched)

One host thread per CPU, each running its engine up to a shared deadline (the quantum end),
then a barrier where device events run and time advances. Device accesses take a lock (or
are sent to the device thread) and use the same "access at the device clock" rule. LL/SC
reservations become an atomic per-line table checked by SC; the rest follows JIT.adoc
"Toward host-parallel vCPUs". This mode is not deterministic run to run, and is only
accepted against reference-mode results on the same workloads (same final outputs, not the
same cycles).

Learned from the reference (2026-10-13), constraints on that design:

* A CPU may not see device time held for 1,000 cycles or more: the PROM's PI_RT_COUNT
  check fails (above). Quanta of that size need each CPU's reads of the real-time counter
  to follow its own time, or a quantum well under 2,000 cycles.
* Device models must not complete work faster than a guest driver's protocol can follow
  from another CPU: the ISP1020 lost a completion that arrived inside IRIX's interrupt
  handler on the other CPU (IP27.adoc "ISP1020"). Expect more of these where devices act
  instantly.
* Measured on one host thread (tier 1, 2026-10-12): the two-CPU boot costs about 1% more
  host time per guest cycle than one CPU; the rest is that both CPUs' cycles run in turn.
  CPU B spends the PROM phase in the firmware's wait loops and much of the IRIX boot in the
  idle loop (`idler`, `local_idle`), so threads mostly reclaim waiting.

== Stages

S0. **Observe** (above). Gate: the facts recorded; the review of this plan with the user.

PI_CPU_PRESENT from the configuration. One CPU still runs. Gates: Hub unit tests (PI_CPU_NUM

Gates: IRIX boots to `login:` with `hinv` reporting two 180 MHz processors and `mpadmin -s`

identical digests and same-cycle snapshots on all three engines; the existing benchmarks.

S4. **Host-parallel CPUs (fast mode).** Gates: the S3 workloads reach the same outputs;
host-parallel speedup measured on the two-CPU workload; reference mode unchanged.

    store on one node can break a reservation on the other (a spurious SC failure, which

  - Snapshots keep the one-node fields; the second node's components save under `node1.`,

    runs on every Hub access: `synchronize_time` stays inlined into it (out of line cost

    slots cost `boot2` 12%), and Coherence skips stores when no other CPU holds a
    reservation (looping over four CPUs on every store cost about 3%).
  - Observed with two nodes and the link down (deskside, two CPUs each): both PROMs run the
    same path in step; on the shared Crossbow each writes its own port's upper arbitration
    register (`0x15c` for n2, `0x19c` for n1), then one clears them all and takes port 9's;
    neither reaches the console (none of the PROM's buffered output appears in 111 s of
    virtual time). Real hardware with two nodes always has the link, so this is not pursued.

=== Target

slate's topology without graphics (ADR-021): one deskside module with node boards n1 and n2,

=== What is known

* slate (OBS-SLATE-0003): "Found 2 objects (2 hubs, 0 routers) in 10464 usec", "Waiting
  for peers to complete discovery", "Global master is /hw/module/1/slot/n2", "4 CPUs on 2
  nodes found", "No. of RTRs enabled = 0": the two Hubs are linked without a router chip.
  Lines prefixed "1A 000:" come before the global master's banner, so more than one CPU prints
  during discovery.
* slate (OBS-SLATE-0004, `local/slate/hinv-mvv.txt`): CPUs 0 and 1 are n2's slices A and B,
  CPUs 2 and 3 n1's; each node has 1024 MB ("Slot 82", "Slot 81"); the module's MODULEID and
  midplane (4P1G5_MPLN) NICs are on n1's MicroLAN; the BaseIO is io1, two QL1040B
  controllers.
* Crossbow ports (IP27.adoc "Crossbow", deskside): n1 is port `0xa`, n2 port 9, the BaseIO 15
  (io1). Both Hubs reach the Crossbow directly.
* The PROM's link test (`0x1fc2df18`, disassembly): NI_STATUS_REV_ID bit 29, the link-up
  bit (LINUX `hubni.h` NSRI_LINKUP). On one node it polls it about 6.4 million times (Hub
  access log of a PROM run) before "Local hub NUMAlink is down". `observed`.
* With the link up, the discovery code that follows (`0x1fc2df2c`) starts a vector operation
  on NI offset `0x600000` (`0x1fc53954`), `inferred`: reading the neighbor Hub's
  NI_STATUS_REV_ID through the link. Vector PIO is the network's route-addressed access,
  used before node IDs are assigned: NI_VECTOR_PARMS (type read, write, exchange),
  NI_VECTOR, NI_VECTOR_DATA, and the results in NI_VECTOR_STATUS, NI_RETURN_VECTOR,
  NI_VECTOR_READ_DATA (LINUX `hubni.h`; storage only today, IP27.adoc "Storage-only
  registers").
* The PROM's vector PIO (disassembly of `0x1fc14c2c`, write, and `0x1fc14ed0`, read; their
  callers pass the route, the data, the NI address, and a result pointer), `observed`:
  read NI_VECTOR_CLEAR (`0x600380`), then NI_VECTOR_STATUS, and give up (-1) if VALID (bit
  63) is still set; for a read, write `0xdeadbeefdeadbeef` to NI_VECTOR_READ_DATA; write
  the route to NI_VECTOR and, for a write, the data to NI_VECTOR_DATA; set an NI_AGE
  register's virtual channel to 1 (`0x600500` or `0x600510`), write NI_VECTOR_PARMS, and
  restore the age register. PARMS holds the address bits 19:3, a write ID in 39:32, a PIO ID
  in 49:40 (`0x7b` for writes, `0x1c8` for reads), and the type in 1:0. It then polls
  NI_VECTOR_STATUS every 100 µs (a count from PROM data) for VALID, retrying the whole
  operation up to eight times (-7 when all time out). Then OVERRUN (bit 62) is -2, and the
  status type (2:0) 4, 5, or 6 is -4, -5, or -6 (address, command, protection error). A
  write succeeds only when the status echoes type 1, the PIO ID, the write ID, and the
  address; a read returns NI_VECTOR_READ_DATA. The address field is an offset in the
  target's NI space: the discovery's read of `0x600000` is the neighbor's NI_STATUS_REV_ID
  (LINUX field masks: NVP_ADDRESS bits 19:3).
* PROM messages give the shape of discovery (strings in the image): the global master reads
  each Hub's NIC ("Could not read remote NIC for nasid %d"), assigns node IDs ("Distributing
  NASIDs", "Notifying Hub: index %d, nic 0x%lx, nasid %d") while the others wait ("Local
  Master: Waiting for my NASID ...", "Local Slave : Waiting for my NASID ..."); a Hub with
  no CPUs is "headless"; "Peer HUB detected on Xbow but no NUMAlink connection" shows each
  PROM also looks for the other Hub on the Crossbow. "04: verbose" is one of the system
  controller's debug switches ("dbg" in POD), which our ELSC model cannot report yet.
* The deskside module type follows from the node slot IDs (IP27.adoc "Machine type"):
  slot ID 3 is n1 on Crossbow port `0xa`, ID 2 is n2 on port 9, and the BaseIO is io1 on
  port 15. The installed IRIX boots unchanged on that layout. Until 2026-10-15 the machine
  used the rack layout (n1 on port 9, the BaseIO on 8), where n1 and n2 are on different
  Crossbows; deskside is now the default (IP27.adoc "Machine type").
* NI_STATUS_REV_ID holds the Hub's node ID in bits 16:8 (LINUX NSRI_NODEID; the PROM reads it
  with mask `0x1ff00`, `observed`); physical address bits 39:32 select the node (PRM §1.2.1);
  before node IDs are assigned they are all zero (PRM §1.2.3).

=== Design

* **The node is the unit.** `Ip27Machine` owns one or two nodes; a node owns its Hub, its
  memory, and its CPUs (the slices). A configuration value `--nodes 1|2` selects them,
  `--cpus` stays per node, and one node stays the default. Node slots follow slate (n1, n2).
* **Requests are routed by node ID.** A request whose node ID (address bits 39:32) is not
  the requester's own goes to the other node's Hub: its memory, its Hub registers (the
  remote-Hub alias), and its PI_INT_PEND_MOD, which is how a CPU interrupts a CPU on the
  other node. Remote memory takes the same virtual time as local memory: no Hub, link, or
  directory latency is modeled, as no cache or memory latency is modeled today.
* **The link is a pair of NI ports.** One link object joins the two Hubs' NIs: link-up
  status in NI_STATUS_REV_ID, and vector PIO along a route (with no router, the empty route
  reaches the neighbor Hub). Its errors, retries, and LLP timing are not modeled until the
  guest is observed to depend on them.
* **One Crossbow, two Hubs.** Each Hub's II is a crosstalk port of the module's Crossbow
  (n1 `0xa`, n2 9); a widget's interrupt goes to the Hub its INTDEST address names.
* **Scheduling generalizes from two CPUs to N.** The CPU with the fewest completed cycles
  runs (the lowest index on a tie) until it is a slice ahead of the next lowest; device time
  is the lowest. With two CPUs this is the current rule, so the two-CPU digests stay the
  same.
* **Snapshots** hold each node's Hub, memory, and CPUs; the one-node format is unchanged.

. Queue two TEST UNIT READY commands to the CD-ROM with interrupts masked at the CPU, and

. Read PCI_INTF_STS and mailbox 5. If the in-pointer advanced by two while bit 2 was set,

== Decisions (with the user, 2026-10-12)

. **Scheduling: time slices of configurable length.** The CPU that is behind runs until it
  is a slice ahead of the other, then they swap. `--cpu-slice CYCLES` sets the
  length: 1 is the strict setting (the CPUs alternate every instruction; every
  interleaving is one the hardware could produce) used by tests and engine comparison; the
  default is about 1 µs (180 cycles at 180 MHz). Exact global order of device accesses was
  not chosen: it makes device accesses more precise but does nothing for memory
  interleaving, where the real machine is itself not repeatable, and needs restartable
  accesses in every engine.
. **The requester is structural: a Hub port per CPU**, each CPU with its own address-space
  view, as each processor has its own SysAD connection into the PI.
. **`--cpus 1|2` per node; one CPU stays the default** until S3's gates pass.
. **Review after S3**, before host-parallel CPUs (S4).

Decisions after the hardening (2026-10-13):

. **S5 before S4** (the user): the second node on one host thread first, so host-parallel
  CPUs are designed once, for four CPUs.
. **The default slice stays 180 cycles** (the user left it to the agent). 1,000 cycles would
  make compute-heavy two-CPU work about 23% faster, but it is half the PROM's bound
  (2,000), and S5 will run guest code not yet seen with several CPUs (discovery across the
  link, the second node's PROM waiting on the first), which may bound the skew more
  tightly; 180 is eleven times inside the known bound. Speed comes from S4, whose quantum
  is designed against the bounds S5 measures; the slice is revisited then. Runs that want
  the speed now pass `--cpu-slice 1000`.

Device time (refined in S2, 2026-10-12): devices and events see virtual time, the time of
the CPU furthest behind. Only that CPU runs past the other, by at most a slice, so virtual
time never goes backwards and a CPU never has to wait in the middle of an instruction; a CPU
ahead of the other sees device time up to one slice behind its own Count. With one CPU this
is exactly the earlier rule. The plan's first wording (the access at the later of the two
clocks, the CPU stalling to it) would have needed every engine to add cycles inside an
instruction.

Asked by the user: why not model the real machine exactly? Its structure is modeled exactly
(two processors, a port each into the Hub, coherent shared memory, IPIs through the Hub's
registers). Its cycle timing is not: the order in which two R10000s reach memory depends on
out-of-order pipelines, cache misses, and Hub queues that no public document specifies, a
cycle-accurate model would be orders of magnitude slower, and real hardware does not
repeat it either. PROM and IRIX are correct under any interleaving the hardware permits, so
the contract is to produce one such interleaving, deterministically in reference mode.
